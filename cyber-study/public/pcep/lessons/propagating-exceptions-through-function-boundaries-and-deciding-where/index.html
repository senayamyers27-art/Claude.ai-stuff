PCEP – Certified Entry-Level Python Programmer PCEP-30-02 · Domain 4: Functions and exceptions

Propagating exceptions through function boundaries and deciding where to handle them

▶ Watch the overview video

Last reviewed October 7, 2026 · Leer en español

Explain it simpler

When something goes wrong inside a function and that function has no plan for it, the problem is passed back to whoever called the function, like a question an employee cannot answer being passed up to a manager. If the manager has no answer either, it goes to their boss, and so on. If it reaches the very top with nobody handling it, the program stops and prints a report called a traceback. Everything the function would have done after the problem is skipped, including handing back a result. Deciding where to catch an error is like deciding who should answer a customer: the person who actually knows what to do, not necessarily the first person who heard the question.

Amara is on call for the online booking system at Heronsgate Community Pool. A parent emails: the site accepted her child's swim-lesson booking, showed a cheerful "Booked for None", and reserved no lane. You trace the flow. The booking page calls create_booking(), which calls pick_slot(), which calls a helper that parses the lesson time. That helper has a tidy try and except that catches every bad time and quietly returns None. Nothing crashed, nothing was logged, and three layers up, the page had no idea anything had failed. Was catching the error there the right call, and if not, where should it have been caught?

An exception does not have to be handled in the function where it is raised. If a function has no matching except for an exception, the function stops immediately, and the exception is passed (propagated) to the code that called it, at the point of the call. If that caller does not handle it either, it moves up again, through each calling function in turn. If it reaches the top level of the program without being handled, Python prints a traceback and the program ends. This behavior is what lets you separate the code that detects a problem from the code that decides what to do about it.
