Implementación de controladores de dominio: Install-ADDSForest / Install-ADDSDomainController, instalación desde medios (IFM), DC de solo lectura y DC en máquinas virtuales de Azure

Un controlador de dominio (DC) es un Windows Server que guarda una copia de escritura o de solo lectura de la base de datos de Active Directory Domain Services (AD DS), autentica usuarios y equipos con Kerberos y replica los cambios con otros DC. Casi todo lo demás en un entorno Windows depende de que los DC estén en buen estado, así que la forma en que los implementas importa. Las directivas de grupo, los permisos de los recursos compartidos, las cuentas de servicio e incluso muchas aplicaciones de negocio dan por hecho, sin decirlo, que hay un DC accesible y que funciona correctamente.

La implementación siempre tiene dos pasos. Primero instalas los binarios del rol con Install-WindowsFeature AD-Domain-Services -IncludeManagementTools. Eso solo copia archivos y agrega las herramientas de administración; el servidor todavía no es un DC. Segundo, promueves el servidor, lo que crea un dominio o se une a uno, genera la base de datos, configura SYSVOL y registra los registros DNS. En Server Manager lo ves como la bandera amarilla de notificación que ofrece Promote this server to a domain controller después de instalar el rol.

La promoción usa uno de tres cmdlets de PowerShell del módulo ADDSDeployment. Install-ADDSForest crea un bosque totalmente nuevo y su primer dominio (raíz); indicas -DomainName, -DomainNetbiosName, los modos de bosque y de dominio y una contraseña del modo de restauración de servicios de directorio (DSRM). Install-ADDSDomainController agrega otro DC a un dominio existente, que es como obtienes redundancia, y es el cmdlet que más ejecutarás en la práctica. Install-ADDSDomain crea un nuevo dominio secundario o de árbol en un bosque existente. Cada cmdlet tiene un gemelo Test- (por ejemplo Test-ADDSDomainControllerInstallation) que ejecuta las comprobaciones de requisitos previos sin cambiar nada, y el asistente de Server Manager puede exportar exactamente el PowerShell que ejecutaría, lo cual es una buena forma de aprender los parámetros.

La instalación desde medios (IFM) resuelve un problema de ancho de banda. Un DC nuevo normalmente descarga toda la base de datos por la red durante su primera replicación, lo que puede saturar durante horas un enlace lento de red de área extensa (WAN). Con IFM ejecutas ntdsutil en un DC existente (activate instance ntds, ifm, create sysvol full C:\IFM) para obtener una copia de la base de datos y de SYSVOL, la llevas al sitio remoto y promueves con -InstallationMediaPath. Así, solo los cambios hechos desde que se crearon los medios se replican por la WAN. Los medios de un DC de escritura pueden crear un DC de escritura o un DC de solo lectura; los medios creados como medios de RODC solo pueden crear un RODC. Trata los medios IFM como información muy sensible, porque contienen los hashes de contraseña de todas las cuentas del dominio; cifra la unidad y destruye la copia después de usarla.

Un controlador de dominio de solo lectura (RODC) está pensado para sucursales con poca seguridad física. Guarda una copia de solo lectura del directorio, así que nadie puede hacer en él cambios que se repliquen al resto del dominio. De forma predeterminada no almacena contraseñas en caché, y solo almacena las credenciales de las cuentas que permitas en su directiva de replicación de contraseñas (Password Replication Policy), que se forma con el grupo Allowed RODC Password Replication Group, el grupo Denied RODC Password Replication Group y las listas propias de cada RODC. Si roban el servidor, restableces solo las contraseñas que estaban en su caché, y la página de propiedades del RODC puede mostrarte exactamente qué cuentas son.

Los RODC también admiten la separación del rol de administrador. Puedes delegar la administración local de un RODC, como instalar controladores o actualizaciones, a un técnico de la sucursal sin convertirlo en Domain Admin. Antes de agregar el primer RODC, el bosque debe tener un DC de escritura con un sistema operativo compatible, y antes se necesitaba adprep /rodcprep; la promoción moderna ejecuta automáticamente la preparación necesaria. En el examen, una sucursal sin seguridad más la necesidad de limitar qué contraseñas se almacenan casi siempre apuntan a un RODC.

Ejecutar DC como máquinas virtuales de Azure extiende tu dominio a la nube, pero Azure tiene reglas específicas. Asigna a la VM una dirección IP privada estática en su interfaz de red (NIC) en Azure, no dentro del sistema operativo invitado. El invitado sigue usando DHCP y Azure siempre le entrega la misma dirección. Configurar una IP estática dentro de Windows puede dejar a la VM aislada de la infraestructura de Azure. Después, apunta los servidores DNS de la red virtual a tus DC para que las demás VM puedan encontrar el dominio.

La distribución de discos es la otra regla de Azure. Coloca la base de datos de AD (NTDS.dit), los registros y SYSVOL en un disco de datos administrado aparte, con el almacenamiento en caché del host configurado en None. El disco del sistema operativo usa caché de escritura de forma predeterminada, lo que puede hacer que AD crea que los datos se escribieron de forma segura cuando no es así, y eso pone en riesgo la base de datos tras un reinicio inesperado. Por último, reparte los DC entre zonas de disponibilidad o en un conjunto de disponibilidad para que una sola falla de hardware no deje fuera a todos los DC, y define un sitio y una subred de AD para la red virtual de Azure para que los clientes y la replicación se comporten de forma razonable.

Así se ve una promoción típica de un DC adicional, con la base de datos y SYSVOL ubicados en un disco de datos montado como F:.

Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Install-ADDSDomainController -DomainName corp.contoso.com -InstallDns `
  -DatabasePath F:\NTDS -LogPath F:\NTDS -SysvolPath F:\SYSVOL `
  -Credential (Get-Credential)

Términos clave

DSRM
Directory Services Restore Mode (modo de restauración de servicios de directorio): un modo de arranque especial para el mantenimiento sin conexión de AD, protegido por una contraseña local que se define durante la promoción.
IFM
Install from media (instalación desde medios): promover un DC a partir de una copia de la base de datos creada con ntdsutil para que la replicación inicial no cruce la WAN.
RODC
Read-only domain controller (controlador de dominio de solo lectura): guarda una copia de solo lectura del directorio y almacena en caché solo las contraseñas que permite su directiva de replicación de contraseñas.
Password Replication Policy (directiva de replicación de contraseñas)
Las listas de permitidos y denegados que deciden qué credenciales de cuentas puede almacenar en caché un RODC.
Host caching (almacenamiento en caché del host)
Una configuración de disco de Azure (None, ReadOnly, ReadWrite); los discos de datos de un DC que contienen NTDS deben usar None.
Install-ADDSDomainController
El cmdlet de ADDSDeployment que promueve un servidor como DC adicional en un dominio existente.
Ejemplo real

Una cadena minorista agrega un DC en una tienda con un enlace lento. El administrador ejecuta IFM con ntdsutil en un DC central, envía los medios cifrados en una unidad USB y promueve un RODC con -InstallationMediaPath. Solo se replican unos pocos megabytes de cambios recientes, y solo las contraseñas del personal de la tienda quedan en la caché local.

Consejo para el examen: En los DC de Azure, la IP estática se configura en la NIC de Azure, no en el invitado, y NTDS va en un disco de datos con caché None. Las respuestas que proponen configurar una IP estática dentro de Windows o dejar NTDS en el disco del sistema operativo son las trampas.

Comprueba lo que sabes

¿Qué cmdlet crea el primer DC de un bosque nuevo y cuál agrega un DC a un dominio existente?

Install-ADDSForest crea un bosque nuevo; Install-ADDSDomainController agrega un DC a un dominio existente.

¿Por qué NTDS.dit debe estar en una VM de Azure en un disco de datos con el almacenamiento en caché del host en None?

El disco del sistema operativo usa caché de escritura, lo que puede romper la suposición de AD de que las escrituras son duraderas y pone en riesgo la base de datos; un disco de datos con caché None lo evita.

¿Qué limita las contraseñas de usuario que almacena un RODC?

Su directiva de replicación de contraseñas, administrada mediante los grupos Allowed y Denied RODC Password Replication Group y la configuración propia de cada RODC.

¿Se pueden usar medios IFM creados como medios de RODC para promover un DC de escritura?

No. Los medios de RODC solo pueden crear un RODC; los medios de un DC de escritura (medios completos) pueden crear cualquiera de los dos tipos.
