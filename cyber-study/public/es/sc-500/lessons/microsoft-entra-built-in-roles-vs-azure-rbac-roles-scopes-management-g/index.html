Microsoft Certified: Cloud and AI Security Engineer Associate (replaces Azure Security Engineer Associate / AZ-500) SC-500

Roles integrados de Microsoft Entra vs roles de Azure RBAC, ámbitos (grupo de administración, suscripción, grupo de recursos, recurso) y privilegio mínimo

Azure tiene dos sistemas de permisos separados, y el examen espera que sepas cuál de ellos responde a una pregunta determinada. Los roles de Microsoft Entra (antes roles de Azure Active Directory) controlan el directorio en sí: usuarios, grupos, registros de aplicaciones, licencias, Conditional Access y la configuración del tenant. El control de acceso basado en roles de Azure (Azure RBAC) controla los recursos de Azure: suscripciones, máquinas virtuales (VM), cuentas de almacenamiento, key vaults y todo lo demás que se administra mediante Azure Resource Manager (ARM). Los dos sistemas los evalúan servicios distintos, así que tener poder en uno no otorga automáticamente poder en el otro. Un Global Administrator puede restablecer las contraseñas de todos pero, de forma predeterminada, no puede eliminar ni una sola VM. Un Owner de una suscripción puede eliminar todas las VM que contiene, pero no puede crear un usuario.

Conviene conocer por su nombre los roles integrados comunes de cada lado, porque las respuestas del examen los presentan como opciones. Entre los roles integrados comunes de Entra están Global Administrator, Privileged Role Administrator, User Administrator, Security Administrator, Security Reader, Application Administrator y Conditional Access Administrator. Entre los roles integrados comunes de Azure RBAC están Owner (control total más el derecho de asignar roles), Contributor (control total pero sin asignación de roles), Reader (solo lectura) y User Access Administrator (solo administrar asignaciones de roles). Role Based Access Control Administrator es un rol integrado más reciente que puede administrar asignaciones de roles y admite condiciones que limitan qué roles puede otorgar. También hay muchos roles específicos de servicio, como Virtual Machine Contributor, Key Vault Secrets User y Storage Blob Data Reader, que suelen ser la respuesta correcta cuando una pregunta insiste en el privilegio mínimo.

Existe un puente deliberado entre los dos sistemas. Un Global Administrator puede activar 'Access management for Azure resources' en la página de propiedades de Microsoft Entra ID, lo que le otorga User Access Administrator en el ámbito raíz (que se muestra como /). Desde ahí puede asignarse a sí mismo o a otra persona un rol en cualquier suscripción. Esto existe para emergencias, como recuperar el control cuando todos los Owner de una suscripción ya dejaron la empresa, y debe desactivarse de nuevo después. El problema de Rosa en la escena inicial se resuelve exactamente así, y la actividad aparece en el registro de actividad de Azure para que pueda auditarse.

Una asignación de rol de Azure RBAC siempre tiene tres partes: una entidad de seguridad (usuario, grupo, entidad de servicio o identidad administrada), una definición de rol (la lista de operaciones permitidas) y un ámbito. Si puedes nombrar las tres, puedes describir cualquier asignación. En la pestaña Role assignments verás filas que se leen como 'Devin, Virtual Machine Contributor, Resource group: rg-loans-prod', que son precisamente esas tres partes.

Los ámbitos forman una jerarquía: grupo de administración, luego suscripción, luego grupo de recursos y luego recurso individual. Los permisos se heredan hacia abajo, así que Reader en un grupo de administración da acceso de lectura a todas las suscripciones, grupos de recursos y recursos que están debajo. Los permisos efectivos son la unión de todas las asignaciones que aplican, y Azure RBAC es aditivo: otorgar Reader en una suscripción no quita el Contributor otorgado en un grupo de recursos que está debajo. Las asignaciones de denegación (deny assignments) existen y sí prevalecen sobre los permisos, pero las crea Azure mismo (por ejemplo, mediante deployment stacks o aplicaciones administradas), no tú directamente. Por eso la respuesta del examen a '¿cómo bloqueo una acción?' rara vez es una asignación de rol.

Privilegio mínimo significa dar a cada identidad solo los permisos que necesita, en el ámbito más reducido y solo durante el tiempo necesario. En la práctica, eso se traduce en unos pocos hábitos. Asigna roles a grupos en lugar de a personas, para que las altas, los cambios de puesto y las bajas se resuelvan con la pertenencia a grupos. Prefiere un rol específico como Virtual Machine Contributor antes que uno amplio como Contributor. Asigna en el grupo de recursos en lugar de la suscripción cuando el trabajo se limita a una aplicación. Usa Privileged Identity Management (PIM) para que los roles poderosos sean elegibles en lugar de permanentes. Limita la cantidad de Owner de suscripciones y de Global Administrator, y mantén un par de cuentas de emergencia (break-glass) excluidas de las directivas riesgosas para que nunca puedas quedarte sin acceso por completo.

Saber dónde vive cada sistema en el portal agiliza la solución de problemas. Azure RBAC se administra en la hoja Access control (IAM) de cualquier ámbito. La pestaña Check access muestra lo que una entidad de seguridad puede hacer en ese ámbito, y Role assignments muestra quién tiene qué, incluidas las asignaciones heredadas desde arriba, que aparecen etiquetadas con el ámbito superior. Los roles de Entra se administran en Microsoft Entra ID, Roles and administrators. Algunos roles de Entra pueden limitarse a una unidad administrativa, de modo que un administrador de la mesa de ayuda solo gestione usuarios de una región o unidad de negocio, que es la versión del lado del directorio de reducir el ámbito.

Por último, ten clara la regla de asignación de roles, porque es un distractor favorito. Entre los roles integrados, solo Owner, User Access Administrator y Role Based Access Control Administrator pueden asignar roles de Azure. Contributor puede hacer casi todo con los recursos, pero no puede dar acceso a nadie, y precisamente por eso es más seguro otorgarlo que Owner.

Términos clave

Microsoft Entra role (rol de Microsoft Entra)
Rol de directorio que otorga permisos sobre objetos de identidad y la configuración del tenant, como User Administrator o Security Administrator.
Azure RBAC role (rol de Azure RBAC)
Definición de rol que otorga permisos sobre recursos de Azure mediante Azure Resource Manager, como Owner, Contributor o Reader.
Scope (ámbito)
Nivel en el que se aplica una asignación de rol: grupo de administración, suscripción, grupo de recursos o recurso; los niveles inferiores la heredan.
User Access Administrator
Rol de Azure RBAC que puede administrar asignaciones de roles, pero no los recursos en sí.
Role assignment (asignación de rol)
Combinación de una entidad de seguridad, una definición de rol y un ámbito que otorga acceso.
Least privilege (privilegio mínimo)
Otorgar solo los permisos necesarios, en el ámbito más reducido y durante el menor tiempo posible.
Ejemplo real

Un desarrollador necesita reiniciar VM en el grupo de recursos app-prod. En lugar de hacerlo Contributor de la suscripción, lo agregas a un grupo que tiene Virtual Machine Contributor solo en ese grupo de recursos. Puede administrar esas VM, pero no puede tocar la red de otros grupos de recursos ni dar acceso a nadie más.

Consejo para el examen: Si la pregunta trata de usuarios, grupos, aplicaciones o configuración del tenant, la respuesta es un rol de Entra; si trata de suscripciones o recursos, es un rol de Azure RBAC. Solo Owner, User Access Administrator y Role Based Access Control Administrator (entre los integrados) pueden asignar roles de Azure; Contributor no puede.

Comprueba lo que sabes

Un Global Administrator no puede ver ninguna suscripción. ¿Cuál es la forma admitida de obtener acceso en una emergencia?

Activar 'Access management for Azure resources' en las propiedades de Entra ID, lo que otorga User Access Administrator en el ámbito raíz; después puede asignarse un rol y debe desactivar la opción al terminar.

Un usuario tiene Reader en la suscripción y Contributor en un grupo de recursos. ¿Qué puede hacer en ese grupo de recursos?

Acciones de Contributor, porque Azure RBAC es aditivo y los permisos efectivos son la unión de todas las asignaciones que aplican.

¿Por qué asignar roles a grupos en lugar de a usuarios individuales?

Las asignaciones a grupos son más fáciles de revisar y cambiar, reducen la proliferación de asignaciones y convierten las altas, cambios de puesto y bajas en una cuestión de pertenencia a grupos.

¿Qué rol debes dar a alguien que debe crear usuarios y restablecer contraseñas, pero no debe administrar VM de Azure?

Un rol de Entra como User Administrator, porque la administración de usuarios es una tarea del directorio; no otorga permisos sobre recursos de Azure.
