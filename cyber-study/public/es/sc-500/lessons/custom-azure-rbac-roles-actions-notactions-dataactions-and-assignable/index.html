Roles personalizados de Azure RBAC: actions, notActions, dataActions y ámbitos asignables

Cuando ningún rol integrado encaja, puedes crear un rol personalizado de control de acceso basado en roles de Azure (Azure RBAC). Un rol personalizado es una definición de rol en JavaScript Object Notation (JSON) que enumera exactamente qué operaciones se permiten. Lo creas en el portal (normalmente clonando un rol existente y editándolo), con Azure PowerShell (New-AzRoleDefinition) o con la interfaz de línea de comandos de Azure (CLI) (az role definition create --role-definition role.json). Los roles personalizados se almacenan en el tenant de Microsoft Entra y pueden compartirse entre las suscripciones que figuran en sus ámbitos asignables, así que un solo rol bien diseñado puede servir a muchos equipos.

Cada permiso de un rol se escribe como una cadena de operación de proveedor de recursos. Algunos ejemplos son Microsoft.Compute/virtualMachines/start/action o Microsoft.Storage/storageAccounts/read. El patrón es proveedor, tipo de recurso y luego una operación como read, write, delete o una acción con nombre. Se permiten comodines: Microsoft.Compute/virtualMachines/* significa todas las operaciones sobre VM, y un * solo significa todas las operaciones sobre todo. Los comodines son cómodos pero peligrosos, porque incluyen automáticamente las operaciones que Microsoft agregue a un proveedor en el futuro.

La propiedad Actions enumera operaciones del plano de control (administración) que pasan por Azure Resource Manager (ARM): crear, leer, actualizar, eliminar y acciones especiales como reiniciar. La propiedad NotActions resta operaciones de un comodín en Actions. Por ejemplo, Actions: ["*"] con NotActions: ["Microsoft.Authorization/*/Delete", "Microsoft.Authorization/*/Write"] es, en esencia, cómo está definido el rol integrado Contributor: todo excepto cambiar el acceso. Leer definiciones integradas como esta es una buena manera de aprender la sintaxis.

El dato más evaluado aquí es que NotActions no es una denegación. Solo quita operaciones de lo que otorga este mismo rol. Si el mismo usuario también tiene otro rol que permite la operación excluida, todavía puede realizarla, porque Azure RBAC es aditivo y los permisos efectivos son la unión de todas las asignaciones. Para bloquear algo de verdad, dependes de la ausencia de permisos, de Azure Policy, de los bloqueos de recursos o de las asignaciones de denegación que crea Azure mismo.

Las operaciones del plano de datos actúan sobre los datos dentro de un recurso, como leer un blob o un mensaje de cola, y se enumeran en DataActions y NotDataActions. Por ejemplo, Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read es una acción de datos, y Microsoft.KeyVault/vaults/secrets/getSecret/action también. Esta división explica por qué Contributor en una cuenta de almacenamiento puede administrar la cuenta, pero no puede leer blobs mediante la autorización de Entra ID; para eso se necesita un rol de datos como Storage Blob Data Reader. Solo los servicios que admiten la autorización de Entra en el plano de datos (Storage, Key Vault con el modelo de permisos RBAC, Service Bus, Event Hubs y otros) tienen acciones de datos.

AssignableScopes enumera dónde se puede asignar el rol personalizado: uno o más grupos de administración, suscripciones o grupos de recursos. Un rol cuyo ámbito asignable es una suscripción se puede asignar en esa suscripción o en cualquier cosa debajo de ella, pero no en otra suscripción. Si una asignación desde el portal o la CLI falla con un error que dice que el rol no está disponible en ese ámbito, revisa primero esta lista. Los roles personalizados que incluyen DataActions no se pueden asignar en el ámbito de grupo de administración, y hay límites a nivel de tenant sobre cuántos roles personalizados puedes crear, así que mantenlos pocos, bien nombrados y reutilizables.

Al juntar las piezas, un rol mínimo de operador se ve como el fragmento siguiente. Observa que cada operación está escrita explícitamente en lugar de usar comodines, que no hay acciones de datos porque los operadores nunca tocan los datos dentro de las VM, y que el rol solo se puede asignar dentro de una suscripción. En la práctica, el identificador de suscripción de ejemplo sería un GUID real. ```json { "Name": "VM Operator", "IsCustom": true, "Description": "Start, stop and restart VMs only", "Actions": [ "Microsoft.Compute/virtualMachines/read", "Microsoft.Compute/virtualMachines/start/action", "Microsoft.Compute/virtualMachines/restart/action", "Microsoft.Compute/virtualMachines/powerOff/action", "Microsoft.Compute/virtualMachines/deallocate/action" ], "NotActions": [], "DataActions": [], "NotDataActions": [], "AssignableScopes": ["/subscriptions/<subscription-id>"] } ```

Crear o actualizar un rol personalizado requiere el permiso Microsoft.Authorization/roleDefinitions/write, que tienen Owner y User Access Administrator. Asignar el rol después es un paso aparte que necesita permiso de asignación de roles en el ámbito de destino. Mantener separados estos dos pasos ayuda cuando una pregunta plantea por qué un administrador junior pudo crear un rol pero no usarlo.

Un flujo de trabajo práctico mantiene los errores pequeños. Busca el rol integrado más parecido y expórtalo con az role definition list --name "Virtual Machine Contributor". Edita el JSON, quita el id y establece IsCustom en true, dale un nombre y una descripción claros, enumera solo las acciones necesarias y define ámbitos asignables tan reducidos como sea posible. Créalo, asígnalo a un usuario o grupo de prueba y usa Check access en la hoja Access control (IAM) para confirmar que el usuario puede hacer exactamente lo que pretendías, y nada más, antes de implementarlo.

Términos clave

Actions
Operaciones del plano de control que permite el rol, como crear o reiniciar una VM.
NotActions
Operaciones que se quitan del comodín de Actions solo para este rol; no es una denegación si otro rol las otorga.
DataActions
Operaciones del plano de datos que permite el rol, como leer blobs o secretos de Key Vault.
NotDataActions
Operaciones del plano de datos que se quitan de un comodín de DataActions solo para este rol.
AssignableScopes (ámbitos asignables)
Los grupos de administración, suscripciones o grupos de recursos donde se puede asignar un rol personalizado.
Ejemplo real

Los operadores deben iniciar, detener y reiniciar VM, pero nunca crearlas ni eliminarlas. Creas 'VM Operator' con Actions para virtualMachines/read, start/action, powerOff/action, restart/action y deallocate/action, estableces AssignableScopes en la suscripción de producción y lo asignas al grupo de operaciones en ese ámbito.

Consejo para el examen: Las preguntas suelen evaluar que NotActions no es una denegación y que leer datos en una cuenta de almacenamiento necesita un rol con DataActions, no Contributor. Atento también a un rol que no se puede asignar porque el ámbito de destino está fuera de sus AssignableScopes.

Comprueba lo que sabes

Un usuario tiene un rol personalizado con NotActions para la eliminación de VM y además tiene Contributor en el mismo grupo de recursos. ¿Puede eliminar una VM?

Sí. NotActions solo recorta lo que otorga ese rol; Contributor sigue permitiendo la eliminación.

¿Qué propiedad contendría Microsoft.KeyVault/vaults/secrets/getSecret/action?

DataActions, porque leer el valor de un secreto es una operación del plano de datos.

¿Qué limita dónde se puede asignar un rol personalizado?

Su lista AssignableScopes; solo se puede asignar en esos ámbitos o debajo de ellos.

¿Qué permiso se necesita para crear o actualizar una definición de rol personalizada?

Microsoft.Authorization/roleDefinitions/write, que tienen Owner y User Access Administrator.
