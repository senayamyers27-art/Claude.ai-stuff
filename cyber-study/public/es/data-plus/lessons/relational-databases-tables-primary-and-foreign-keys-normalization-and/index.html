Bases de datos relacionales: tablas, claves primarias y foráneas, normalización y relaciones

Una base de datos relacional almacena datos en tablas, también llamadas relaciones. Cada tabla describe un tipo de cosa, como clientes, productos o pedidos. Cada fila es una instancia de esa cosa, y cada columna es un atributo con un tipo de dato definido, como un entero para una cantidad o una fecha para la fecha del pedido. La mayoría de los sistemas de negocio, incluidas las aplicaciones de ventas, finanzas y recursos humanos (HR), guardan sus datos en bases de datos relacionales como PostgreSQL, MySQL, SQL Server u Oracle, y se consultan con el lenguaje de consulta estructurado (SQL). Entender cómo se conectan estas tablas es lo que permite a un analista escribir combinaciones (joins) correctas y detectar problemas de calidad de datos.

La clave primaria es el ancla de cada tabla. Es la columna, o combinación de columnas, que identifica de forma única cada fila. No puede ser nula ni repetirse, y la base de datos hace cumplir ambas reglas, rechazando una inserción que crearía un duplicado. CustomerID en una tabla Customers es una clave primaria típica. Una clave formada por dos o más columnas es una clave compuesta, por ejemplo OrderID más LineNumber en una tabla de líneas de pedido, donde ninguna columna por sí sola es única pero el par sí lo es. Una clave natural proviene del negocio, como un número de identificación fiscal o una dirección de correo. Una clave sustituta es un número artificial que genera la base de datos, a menudo un entero autoincremental, que se mantiene estable aunque cambien los valores del negocio. Esa estabilidad es la razón por la que muchos diseñadores prefieren las claves sustitutas: los correos cambian, pero el CustomerID 1047 no.

Las claves foráneas son la forma en que las tablas apuntan unas a otras. Una clave foránea es una columna de una tabla que hace referencia a la clave primaria de otra tabla, así que Orders.CustomerID apunta a Customers.CustomerID. La base de datos puede entonces hacer cumplir la integridad referencial: rechaza un pedido de un cliente que no existe y puede impedir que se elimine un cliente que todavía tiene pedidos. Cuando ves un error como 'violates foreign key constraint' en un registro de carga, es esta regla haciendo su trabajo. Los datos copiados a hojas de cálculo o cargados sin restricciones pierden esta protección, y así es como se cuelan los registros huérfanos, es decir, filas cuya clave foránea no coincide con nada.

Las relaciones entre tablas tienen una cardinalidad, que describe con cuántas filas de un lado pueden relacionarse las filas del otro. La de uno a muchos es la más común: un cliente puede tener muchos pedidos, pero cada pedido pertenece a un solo cliente, y la clave foránea está en el lado de 'muchos'. La de uno a uno es menos frecuente, como una persona y su registro de pasaporte, y a veces se usa para separar en su propia tabla columnas poco usadas o sensibles. La de muchos a muchos, como estudiantes y cursos, no se puede guardar con una sola clave foránea. Necesita una tabla de unión, también llamada tabla puente o asociativa, que contenga ambas claves. Una tabla Enrollments con StudentID y CourseID convierte una relación de muchos a muchos en dos relaciones de uno a muchos, y el par de columnas suele formar su clave primaria compuesta.

La normalización es el proceso de organizar las tablas para reducir la redundancia y los problemas de actualización. Sin ella, aparecen anomalías de actualización (cambiar un valor en una fila pero no en sus copias), anomalías de inserción (no poder registrar un producto nuevo hasta que alguien lo pida) y anomalías de eliminación (perder los datos de un cliente al borrar su único pedido). Las formas normales se construyen unas sobre otras. En la primera forma normal (1NF), cada columna contiene un solo valor atómico, sin listas dentro de una celda como 'rojo, azul, verde' y sin grupos de columnas repetidas como Phone1, Phone2 y Phone3.

Las dos formas normales siguientes tratan las dependencias. En la segunda forma normal (2NF), la tabla ya está en 1NF y cada columna que no es clave depende de toda la clave primaria, no de una parte de una clave compuesta. En una tabla de líneas de pedido con clave OrderID más ProductID, el nombre del producto depende solo de ProductID, así que pertenece a la tabla Products. En la tercera forma normal (3NF), la tabla está en 2NF y las columnas que no son clave dependen solo de la clave, no de otras columnas que no son clave. La ciudad de un cliente depende del cliente, no del pedido, así que no debe guardarse en cada fila de pedido; pertenece a la tabla Customers, una sola vez. Un resumen habitual es que cada columna que no es clave debe depender de la clave, de toda la clave y de nada más que la clave.

Los diseños normalizados convienen a los sistemas transaccionales porque cada hecho se guarda una sola vez, así que las actualizaciones son rápidas y consistentes y la base de datos se mantiene pequeña. El costo es que el análisis necesita muchas combinaciones para reconstruir el panorama completo, lo que alarga las consultas y puede hacer más lentos los reportes grandes. Por eso los sistemas de reportes suelen desnormalizar, copiando atributos descriptivos en tablas más anchas para que las consultas sean más simples y rápidas. Ninguna opción es incorrecta. El diseño adecuado depende de si la carga de trabajo consiste en escribir muchas transacciones pequeñas, lo que favorece la normalización, o en leer grandes cantidades de datos para el análisis, lo que tolera e incluso prefiere cierta redundancia.

Para el examen y para el trabajo diario, relaciona cada concepto con un síntoma. Los datos del cliente duplicados en cada fila de pedido indican que falta un paso de normalización. Los pedidos que no coinciden con ningún cliente indican una clave foránea ausente o que no se hace cumplir. Dos filas con el mismo ID supuestamente único indican un problema de clave primaria. Y cuando una combinación multiplica de repente la cantidad de filas, revisa si combinaste sobre una relación de muchos a muchos sin pasar por la tabla de unión.

Términos clave

Primary key (clave primaria)
Una columna o conjunto de columnas cuyos valores identifican de forma única cada fila y nunca son nulos.
Foreign key (clave foránea)
Una columna que hace referencia a la clave primaria de otra tabla, vinculando las tablas y haciendo cumplir la integridad referencial.
Composite key (clave compuesta)
Una clave primaria formada por dos o más columnas que son únicas solo en combinación.
Surrogate key (clave sustituta)
Un identificador generado por el sistema, como un entero autoincremental, sin significado de negocio.
Normalization (normalización)
Organizar las tablas en formas normales (1NF, 2NF, 3NF) para que cada hecho se almacene una sola vez, reduciendo la redundancia y las anomalías de actualización.
Junction table (tabla de unión)
Una tabla que contiene pares de claves foráneas y resuelve una relación de muchos a muchos.
Referential integrity (integridad referencial)
La regla de que cada valor de clave foránea debe coincidir con un valor de clave primaria existente en la tabla referenciada.
Ejemplo real

Una tienda pequeña guardaba los pedidos en una sola hoja de cálculo, con el nombre, el correo y la dirección del cliente repetidos en cada fila. Cuando un cliente cambiaba de correo, algunas filas se actualizaban y otras no. Pasar a una tabla Customers (con CustomerID como clave primaria) y una tabla Orders con CustomerID como clave foránea hace que el correo se guarde una sola vez y que cada pedido se vincule al valor actual. Agregar una tabla Products y una tabla OrderLines con clave OrderID más LineNumber elimina los nombres de producto repetidos, y la restricción de clave foránea impide que alguien ingrese un pedido para un número de cliente que no existe.

Consejo para el examen: Si una pregunta pide qué columna vincula dos tablas, la respuesta es la clave foránea en la tabla del lado 'muchos'. Si pregunta qué elimina los datos del cliente repetidos en cada fila de pedido, la respuesta es la normalización. Si pregunta cómo modelar una relación de muchos a muchos, la respuesta es una tabla de unión.

Comprueba lo que sabes

¿Cómo se modela una relación de muchos a muchos entre estudiantes y cursos?

Se crea una tabla de unión, como Enrollments, con las claves foráneas StudentID y CourseID (que juntas suelen formar una clave primaria compuesta).

¿Por qué una base de datos de reportes podría desnormalizar los datos a propósito?

Menos combinaciones hacen que las consultas analíticas sean más simples y rápidas, y los sistemas de reportes tienen sobre todo lecturas, así que la redundancia es una compensación aceptable.

¿Qué evita la integridad referencial?

Evita valores de clave foránea que no coinciden con ninguna clave primaria, como un pedido de un cliente inexistente, y puede impedir que se elimine una fila padre que todavía tiene filas hijas relacionadas.
