Hubs, proyectos y recursos de Azure AI Foundry frente a recursos de Azure AI services de un solo servicio y multiservicio

Antes de poder llamar a cualquier servicio de IA necesitas un recurso de Azure que te dé un endpoint, credenciales y una factura. El examen espera que conozcas los tipos de recursos y cuándo conviene cada uno. Azure ha cambiado los nombres de esta área varias veces: Azure AI Studio pasó a ser Azure AI Foundry y después Microsoft Foundry, y el recurso que antes se llamaba Cognitive Services ahora es Azure AI services. El tipo de recurso en las plantillas sigue siendo Microsoft.CognitiveServices/accounts, así que verás el nombre antiguo en el código, en nombres de roles como Cognitive Services User y en comandos de la CLI como az cognitiveservices. No dejes que los nombres te distraigan; concéntrate en lo que ofrece cada recurso.

La opción más sencilla es el recurso de un solo servicio. Un recurso de un solo servicio ofrece un servicio, como Language, Speech o Custom Vision, con su propio endpoint y sus propias claves. Es útil cuando quieres un nivel Free (F0) para ese servicio, facturación separada por servicio o claves que solo puedan llamar a una API. Ese último punto es una ventaja de seguridad discreta: si se filtra una clave de un recurso que solo tiene Translator, el atacante solo puede traducir texto, no analizar documentos ni llamar a las API de voz. En el portal lo creas buscando el servicio concreto, como Language service, y aparece con los niveles de precios propios de ese servicio.

El recurso multiservicio agrupa muchos servicios. Un recurso multiservicio de Azure AI services expone muchos servicios (Vision, Language, Speech, Translator, Document Intelligence y más) detrás de un endpoint y un par de claves, con una sola factura. Es la opción más simple cuando una aplicación usa varios servicios, porque la aplicación guarda un endpoint y una clave en lugar de cinco. También es el recurso que adjuntas a un conjunto de habilidades (skillset) de Azure AI Search para pagar el enriquecimiento con IA, cuando durante la indexación se ejecutan habilidades integradas como OCR, reconocimiento de entidades o extracción de frases clave. La contrapartida es que una clave filtrada abre todos los servicios incluidos y no puedes elegir un nivel distinto por servicio.

Azure AI Foundry es la capa para la IA generativa. Es el portal y la plataforma para crear aplicaciones y agentes de IA generativa. Un proyecto de Foundry es el espacio de trabajo donde implementas modelos, creas agentes, ejecutas evaluaciones y usas los playgrounds. Al abrir un proyecto ves páginas para las implementaciones de modelos, el playground de chat, los agentes, las evaluaciones, los recursos conectados y el endpoint y las claves del proyecto. Un proyecto es la unidad en la que un equipo trabaja día a día.

Hay dos formas de alojar proyectos. Los proyectos pueden vivir en un recurso de Azure AI Foundry (un recurso de Azure AI services que además admite proyectos), que es la configuración más simple y más reciente. La configuración más antigua basada en hubs usa un hub de Azure AI, construido sobre Azure Machine Learning: el hub guarda configuración compartida como las conexiones a otros recursos, la red, el proceso y la seguridad, y los equipos crean proyectos debajo de él. Un hub también trae recursos dependientes, como una cuenta de almacenamiento y un Key Vault, que verás aparecer en el grupo de recursos cuando se crea el hub. Los proyectos basados en hubs siguen siendo relevantes para funciones con raíz en Azure Machine Learning, mientras que el recurso de Foundry es el camino que toman los proyectos nuevos.

Elige según lo que se comparte y lo que se aísla. Si varios equipos necesitan conexiones y gobernanza comunes pero espacios de trabajo separados, crea un hub (o un recurso de Foundry) con un proyecto por equipo o aplicación. La configuración de seguridad, como la red privada y las identidades administradas, se define una vez en el nivel compartido, y las implementaciones, prompts, datos y evaluaciones de cada equipo se quedan en su propio proyecto. Si una aplicación solo necesita llamar a una o dos API precompiladas, basta con un recurso de un solo servicio o multiservicio sin Foundry, y agregar Foundry solo sumaría piezas que administrar.

Las conexiones mantienen los secretos fuera del código. Las conexiones de un proyecto guardan cómo llegar a otros recursos, como un servicio de Azure AI Search o una cuenta de almacenamiento, para que los desarrolladores no peguen claves en el código. Una conexión puede usar una clave o, mejor aún, Microsoft Entra ID con una identidad administrada. Cuando un desarrollador agrega sus propios datos en el playground, el proyecto usa su conexión con el servicio de búsqueda en lugar de pedir una clave. Las conexiones creadas en el nivel del hub se comparten con todos sus proyectos, y esa es una de las razones principales para tener un hub.

Sea lo que sea que crees, obtienes una URL de endpoint y, a menos que el acceso por clave esté deshabilitado, dos claves, que se muestran en la página Keys and Endpoint del recurso. Los recursos se crean en una región, y no todos los servicios o modelos están disponibles en todas las regiones, así que elegir la región es parte de la decisión del recurso, algo que el siguiente tema trata en detalle. Como guía rápida de decisión: un servicio y un nivel gratuito apunta a un solo servicio; varios servicios precompilados y una factura apunta a multiservicio; IA generativa con playgrounds, agentes y evaluaciones apunta a un proyecto de Foundry; y varios equipos que comparten gobernanza apunta a un hub o recurso de Foundry con varios proyectos.

Términos clave

Single-service resource (recurso de un solo servicio)
Un recurso de Azure para un solo servicio de IA, con su propio endpoint, claves, nivel de precios y factura.
Multi-service resource (recurso multiservicio)
Un recurso de Azure AI services que expone muchos servicios de IA detrás de un endpoint y un par de claves, con facturación combinada.
Hub
Un contenedor compartido de Azure AI Foundry, construido sobre Azure Machine Learning, que guarda conexiones, seguridad y proceso para varios proyectos.
Project (proyecto)
Un espacio de trabajo de Foundry donde implementas modelos, creas agentes, evalúas y administras los recursos de una aplicación o un equipo.
Connection (conexión)
Una definición guardada y reutilizable de cómo un proyecto llega a otro recurso, como Azure AI Search o el almacenamiento, para que las claves queden fuera del código.
Azure AI Foundry resource (recurso de Azure AI Foundry)
Un recurso de Azure AI services que también admite proyectos de Foundry, la forma más nueva y sencilla de alojar proyectos sin un hub.
Ejemplo real

Una consultora lleva tres pilotos de clientes. Crea un hub con red privada y una conexión a un servicio compartido de Azure AI Search, y luego un proyecto por cliente, para que las implementaciones, prompts y evaluaciones de cada equipo queden separados mientras la gobernanza se define una sola vez.

Consejo para el examen: Si la pregunta insiste en un endpoint y una factura para varios servicios precompilados, elige el recurso multiservicio. Si insiste en un nivel Free o en claves separadas por servicio, elige recursos de un solo servicio. Gobernanza compartida con espacios de trabajo separados significa un hub con proyectos.

Comprueba lo que sabes

Una aplicación usa Vision, Language y Translator, y finanzas quiere una sola factura. ¿Qué deberías crear?

Un recurso multiservicio de Azure AI services, que ofrece un endpoint, un par de claves y facturación combinada.

¿Qué ofrece un hub que un proyecto por sí solo no ofrece?

Configuración compartida para muchos proyectos: conexiones a otros recursos, red, proceso y directivas de seguridad, además del almacenamiento y el Key Vault dependientes.

¿Por qué un equipo de seguridad podría preferir un recurso de un solo servicio para una aplicación que solo traduce texto?

Una clave filtrada solo puede llamar a ese servicio, y el recurso se puede facturar y asignar a un nivel por separado, lo que limita el impacto de un compromiso.
