Dockerfiles para apps de Python: imágenes base, compilaciones multietapa, usuarios no root y .dockerignore

Un Dockerfile es la receta que convierte tu código fuente de Python en una imagen de contenedor: un paquete de solo lectura, organizado en capas, que contiene el espacio de usuario de un sistema operativo, el runtime de Python, tus dependencias y tu código. Todos los servicios de contenedores de Azure de este examen ejecutan imágenes construidas así, incluidos Azure App Service, Azure Container Apps, los trabajos de Container Apps y AKS (Azure Kubernetes Service). Como todos parten de la misma imagen, un Dockerfile limpio es la primera habilidad sobre la que se construye el resto del dominio, y los errores que cometas aquí acompañan a la imagen a todos los entornos.

Empieza por la imagen base en la línea FROM, porque define la mayor parte del tamaño de la imagen y la mayoría de las vulnerabilidades que reportará un escáner. Las imágenes oficiales de Python vienen en varias variantes. La imagen completa basada en Debian es grande, pero incluye compiladores y herramientas de compilación. Las imágenes -slim eliminan la mayoría de esas herramientas y son la opción habitual en producción. Las imágenes Alpine son diminutas, pero usan musl en lugar de glibc como biblioteca de C, así que muchos wheels de Python precompilados no sirven y los paquetes deben compilarse desde el código fuente; en la práctica, eso suele hacer que las compilaciones sean más lentas y que la imagen final sea más grande de lo esperado. Elijas lo que elijas, fija una etiqueta de versión específica, por ejemplo una versión menor de Python más -slim, como python:3.12-slim, en lugar de latest. Una etiqueta fija significa que una recompilación el próximo mes produce el mismo runtime que probaste, no el que resulte ser el más nuevo en ese momento.

Después, piensa en las capas y la caché, porque determinan qué tan rápido recompilas. Cada instrucción como RUN, COPY o ADD crea una capa, y Docker guarda cada capa en caché. Cuando una instrucción y sus entradas no cambian, Docker reutiliza la capa en caché; en cuanto una capa cambia, todas las capas posteriores se vuelven a compilar. Por eso conviene ordenar las instrucciones de la que cambia con menos frecuencia a la que cambia con más. Copia primero requirements.txt, ejecuta pip install --no-cache-dir -r requirements.txt y solo entonces copia el resto del código. Así, un cambio que solo toca el código reutiliza la capa de dependencias en caché en vez de reinstalar todos los paquetes. En un registro de compilación se nota la diferencia: los pasos en caché aparecen marcados como tales y terminan al instante, mientras que un archivo mal ordenado reinstala todo en cada commit. La opción --no-cache-dir además mantiene la caché de descargas de pip fuera de la capa.

Una compilación multietapa (multi-stage build) es la herramienta principal para mantener la imagen final pequeña y limpia. Usa más de un FROM. La primera etapa, a menudo llamada builder, tiene compiladores y encabezados e instala tus dependencias en un entorno virtual. La etapa final vuelve a empezar desde una imagen de runtime pequeña y usa COPY --from=builder para traer solo el entorno virtual terminado y tu código. Todo lo que vivió únicamente en la etapa builder, como herramientas de compilación, cachés, archivos temporales o credenciales usadas para descargar paquetes privados, nunca llega a la imagen final. Eso reduce tanto el tamaño como la superficie de ataque, es decir, la cantidad de herramientas que un atacante podría usar si lograra entrar. El siguiente ejemplo muestra el patrón.

FROM python:3.12-slim AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.12-slim
RUN useradd --create-home appuser
COPY --from=builder /opt/venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
WORKDIR /app
COPY . .
USER appuser
EXPOSE 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]

Fíjate en con qué usuario se ejecuta el proceso, porque de forma predeterminada un proceso de contenedor se ejecuta como root. Si un atacante explota una falla en tu app, ser root dentro del contenedor le facilita mucho modificar archivos, instalar herramientas e intentar escapar del contenedor. La solución son dos líneas: crea un usuario sin privilegios (aquí con useradd) y cámbiate a él con USER antes de CMD, como en el ejemplo. Todas las instrucciones posteriores y la app en ejecución usan entonces esa cuenta. Un detalle relacionado es el puerto. Los usuarios que no son root no pueden enlazar puertos menores que 1024 sin capacidades adicionales de Linux, así que la app escucha en un puerto alto como 8000. Luego le indicas al servicio de hospedaje qué puerto usar, por ejemplo el puerto de destino en Container Apps o la configuración WEBSITES_PORT en App Service. EXPOSE documenta el puerto, pero no lo publica por sí solo.

Por último, controla qué se envía a la compilación con .dockerignore. Funciona como .gitignore, pero para el contexto de compilación, que es el conjunto de archivos que se envía al builder cuando ejecutas una compilación. Los archivos listados en .dockerignore nunca se envían. Las entradas típicas son .git, __pycache__, entornos virtuales locales como .venv, datos de prueba y, sobre todo, archivos .env y archivos locales de credenciales. Hay dos razones. Primero, velocidad: un contexto más pequeño se sube y se compila más rápido, lo que importa sobre todo en compilaciones remotas que suben el contexto, como az acr build. Segundo, confidencialidad: un COPY . . amplio copia todo el contexto en una capa, y cualquiera que pueda descargar la imagen puede extraer esa capa y leer el archivo, aunque una instrucción posterior lo borre.

En conjunto, estos cuatro hábitos responden la mayoría de las preguntas sobre Dockerfiles del examen. Una imagen base slim con versión fija mantiene las compilaciones predecibles. El orden correcto de las instrucciones mantiene rápidas las recompilaciones. Una compilación multietapa deja los compiladores y los secretos de compilación fuera de la imagen final. Un USER que no sea root limita el daño si la app se ve comprometida, y .dockerignore impide que archivos sensibles o voluminosos lleguen siquiera al builder. Cuando una pregunta describa un síntoma, relaciónalo con el hábito: recompilaciones lentas apuntan al orden de las capas, una imagen grande con herramientas de compilación apunta a la compilación multietapa, un archivo filtrado apunta a .dockerignore y un hallazgo de seguridad sobre root apunta a USER.

Términos clave

Base image (imagen base)
La imagen indicada en FROM sobre la que se construye tu imagen, como una imagen slim de Python con versión fija.
Multi-stage build (compilación multietapa)
Un Dockerfile con varias etapas FROM en el que la etapa final copia solo los artefactos necesarios de las etapas anteriores.
Build context (contexto de compilación)
El conjunto de archivos que se envía al builder con una compilación; .dockerignore quita archivos de él.
Layer cache (caché de capas)
La reutilización que hace Docker de los resultados de instrucciones sin cambios, lo que hace que el orden de las instrucciones importe para la velocidad de compilación.
USER instruction (instrucción USER)
Define el usuario que usan las instrucciones posteriores y el contenedor en ejecución, para que la app no tenga que ejecutarse como root.
.dockerignore
Un archivo que lista rutas excluidas del contexto de compilación, por lo que nunca pueden copiarse a la imagen.
Ejemplo real

La imagen de FastAPI de un equipo pesaba 1.1 GB y recompilaba todas las dependencias en cada commit. Cambiaron a una base slim, copiaron requirements.txt antes del código, agregaron una etapa builder para los wheels compilados y un .dockerignore que excluye .git y .env. La imagen final bajó a unos cientos de megabytes, las recompilaciones tras cambios solo de código tardaban segundos y un escaneo de seguridad ya no marcó un archivo .env filtrado.

Consejo para el examen: Si una pregunta pide cómo dejar compiladores o secretos fuera de la imagen final, la respuesta es una compilación multietapa; si pide cómo evitar que ciertos archivos se envíen siquiera a la compilación, la respuesta es .dockerignore.

Comprueba lo que sabes

¿Por qué debes copiar requirements.txt y ejecutar pip install antes de copiar el resto del código fuente?

Porque las capas se guardan en caché en orden; así, los cambios de código reutilizan la capa de dependencias en caché en vez de reinstalar todos los paquetes.

¿Qué mejora una compilación multietapa y cómo lo logra?

El tamaño y la seguridad de la imagen: las herramientas de compilación viven solo en una etapa anterior y la etapa final usa COPY --from para tomar únicamente los artefactos compilados.

¿Por qué ejecutar la app con un USER distinto de root?

Para limitar lo que un atacante puede hacer si la app se ve comprometida; ser root en el contenedor facilita la manipulación y los intentos de escape.

¿Qué archivo evita que un archivo .env local se envíe siquiera al builder?

.dockerignore, porque quita los archivos listados del contexto de compilación antes de que cualquier instrucción COPY pueda verlos.
