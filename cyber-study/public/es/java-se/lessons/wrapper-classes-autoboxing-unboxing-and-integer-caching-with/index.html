Clases envoltorio, autoboxing/unboxing y la caché de Integer con ==

Cada tipo primitivo tiene una clase envoltorio en java.lang: Byte, Short, Integer, Long, Float, Double, Character y Boolean. Fíjate en los dos nombres que no son simplemente el primitivo con mayúscula: Integer para int y Character para char. Los envoltorios existen porque las colecciones y los genéricos solo funcionan con objetos, así que no puedes escribir List<int> y debes escribir List<Integer>. Un objeto envoltorio es inmutable, es decir, el valor que contiene nunca cambia, y una referencia a un envoltorio puede ser null, algo que un primitivo nunca puede ser.

El autoboxing es la conversión automática que hace el compilador de un primitivo a su envoltorio, y el unboxing es lo contrario. Cuando escribes Integer n = 5; el compilador inserta en silencio Integer.valueOf(5), y cuando escribes int m = n; inserta n.intValue(). El unboxing también ocurre cuando un envoltorio se usa con operadores aritméticos o relacionales, así que n + 1 y n > 0 hacen unboxing primero. Como el unboxing es en realidad una llamada a un método, hacer unboxing de una referencia null lanza una NullPointerException (NPE) en tiempo de ejecución. El escenario frecuente en el examen es Map.get devolviendo null para una clave inexistente y ese null asignado a una variable int. El código compila sin problemas y solo falla al ejecutarse.

Conoce la diferencia entre las dos familias de conversión. Integer.parseInt("42") devuelve un int primitivo, mientras que Integer.valueOf("42") devuelve un objeto Integer; ambos lanzan NumberFormatException con texto que no es un número. Los constructores de los envoltorios, como new Integer(5), están obsoletos y marcados para eliminación, así que el código moderno y las respuestas del examen usan valueOf o autoboxing. El boxing solo va al envoltorio correspondiente: Long x = 5; no compila, porque 5 es un int y se convertiría en un Integer, que no es un Long. Java no ensancha y luego hace boxing en un solo paso, así que escribe 5L. Del mismo modo, Double d = 1; falla, mientras que double d = 1; está bien porque es un ensanchamiento simple.

El operador == entre dos referencias a envoltorios compara identidad, es decir, si ambas referencias apuntan al mismo objeto, no si los valores son iguales. Integer.valueOf mantiene una caché de objetos Integer para al menos el rango de -128 a 127, y el autoboxing usa valueOf, así que dos valores con boxing dentro de ese rango apuntan al mismo objeto en caché. Fuera de ese rango, cada boxing normalmente crea un objeto nuevo. Por eso Integer a = 127, b = 127; a == b es true, pero la misma prueba con 128 es false. Short y Long guardan en caché el mismo rango, Byte guarda en caché todos sus valores posibles (que son ese mismo rango), Character guarda de 0 a 127, y Boolean solo tiene los dos objetos compartidos Boolean.TRUE y Boolean.FALSE. Float y Double no tienen esa caché. La solución es sencilla: compara los valores de los envoltorios con equals.

Mezclar un envoltorio y un primitivo en == funciona de otra manera. Se hace unboxing del envoltorio, así que la comparación es numérica y la caché no importa en absoluto. También cuidado con equals entre tipos distintos. Long.valueOf(1).equals(1) es false, porque el argumento 1 se convierte en un Integer, y Long.equals devuelve false para cualquier cosa que no sea un Long. La misma trampa aparece cuando se le pregunta a un Set<Long> si contains(1): la respuesta es false.

Integer a = 100, b = 100;
Integer c = 1000, d = 1000;
System.out.println(a == b);      // true  (cached)
System.out.println(c == d);      // false (different objects)
System.out.println(c.equals(d)); // true
int e = 1000;
System.out.println(c == e);      // true  (c is unboxed)
Long big = 1L;
System.out.println(big.equals(1)); // false (Integer argument)

La resolución de sobrecarga también involucra el boxing, y el compilador trabaja en tres fases. Primero busca una coincidencia exacta o una conversión primitiva de ensanchamiento, sin ningún boxing. Solo si nada encaja intenta boxing y unboxing. Solo si eso también falla considera los varargs. Así que, dados m(long) y m(Integer), la llamada m(5) elige m(long), porque el ensanchamiento le gana al boxing. Si solo existe m(Object), la llamada m(5) igual compila: 5 se convierte en Integer y luego se ensancha como referencia a Object. Lo que el compilador nunca hará es ensanchar un primitivo y después hacer boxing, por eso m(Long) no puede aceptar m(5).

En la práctica, los hábitos seguros son pocos. Usa primitivos para la aritmética local y los contadores, usa envoltorios cuando una colección o un valor que puede faltar los requiera, compara los valores de los envoltorios con equals o haciendo unboxing de uno de los lados, y protégete contra null antes del unboxing, por ejemplo con Map.getOrDefault o una verificación explícita de null.

Términos clave

Wrapper class (clase envoltorio)
Una clase inmutable como Integer o Double que contiene un valor primitivo como objeto.
Autoboxing
La conversión automática de un primitivo a su envoltorio, que el compilador realiza mediante valueOf.
Unboxing
La conversión automática de un envoltorio a su primitivo; lanza NullPointerException si la referencia es null.
Integer cache (caché de Integer)
Un conjunto de objetos Integer, al menos de -128 a 127, que Integer.valueOf reutiliza, lo que hace que == parezca funcionar con valores pequeños.
parseInt vs valueOf
parseInt devuelve un int primitivo; valueOf devuelve un objeto Integer, posiblemente tomado de la caché.
Ejemplo real

Una tienda cuenta los pedidos por cliente en un Map<String, Integer>. El código int count = counts.get(id); funciona en las pruebas y luego falla en producción con una NullPointerException la primera vez que aparece un cliente nuevo, porque get devuelve null y el unboxing falla. Usar getOrDefault(id, 0) lo evita.

Consejo para el examen: Cuando veas == entre dos variables Integer, revisa si ambos valores están entre -128 y 127. Si lo están, espera true; si no, espera false. Si uno de los lados es un primitivo, es una comparación numérica simple.

Comprueba lo que sabes

¿Qué imprime Integer x = 128, y = 128; System.out.println(x == y);?

Normalmente false. 128 está fuera del rango de caché garantizado, así que cada boxing crea un objeto distinto y == compara identidad.

¿Compila Long total = 10;?

No. 10 es un int, y el autoboxing solo produce un Integer, que no se puede asignar a Long. Escribe 10L.

¿Qué pasa cuando se ejecuta Integer n = null; int m = n;?

Compila, pero lanza una NullPointerException, porque el unboxing llama a intValue() sobre null.

¿Cuál es el tipo de retorno de Integer.parseInt("7")?

int, un primitivo. Integer.valueOf("7") devolvería un objeto Integer.
