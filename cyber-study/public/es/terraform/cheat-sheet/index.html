Dominio 1: Infrastructure as Code (IaC) with Terraform (8%)

Consejos para el examen

  • Las preguntas del examen definen IaC por sus propiedades: código guardado en control de versiones y aplicado por una herramienta. Si una respuesta describe documentar pasos manuales o automatizar clics en la consola sin una fuente de verdad, no es el beneficio de IaC por el que se pregunta.
  • Si una pregunta te pide qué beneficio de IaC permite ver quién cambió la infraestructura y cuándo, la respuesta es el control de versiones y el historial de auditoría; si pregunta por entornos de desarrollo y producción idénticos, la respuesta es la consistencia.
  • El examen lo formula como "Terraform es declarativo: describes el estado final deseado". Si una respuesta dice que Terraform ejecuta tus pasos en el orden en que los escribiste, es incorrecta; el orden de los bloques en los archivos no importa.
  • Espera una pregunta de verdadero o falso del tipo "ejecutar terraform apply dos veces sin cambios en la configuración creará recursos duplicados". Es falso: Terraform es idempotente y la segunda ejecución no hace cambios.
  • Si te preguntan qué componente contiene el código que habla con la API de una nube, la respuesta es el provider, no Terraform core. Core se encarga del lenguaje, el grafo, el estado y el flujo de trabajo.
  • Las preguntas del examen comparan Terraform con CloudFormation o las plantillas ARM: la ventaja de Terraform es gestionar muchos providers, incluidas varias nubes, con un solo flujo de trabajo. No es que el mismo bloque de recurso funcione en todas las nubes.
  • Si una pregunta te pide si Terraform puede gestionar cosas como equipos de GitHub, registros DNS o paneles de monitoreo, la respuesta es sí, siempre que exista un provider para la API del servicio.
  • Cuando el examen pregunte qué herramienta es la mejor para crear redes e instancias en la nube, elige Terraform; para gestionar paquetes y archivos dentro de servidores en ejecución, elige la gestión de configuración. Los provisioners son un último recurso.
  • Debes saber que el orden de reemplazo predeterminado de Terraform es destruir y luego crear, y que create_before_destroy lo invierte. En la salida del plan, -/+ significa reemplazar (destruir y luego crear), mientras que +/- significa crear y luego destruir.

Términos clave

Infrastructure as Code (IaC, infraestructura como código)
Gestión de la infraestructura mediante archivos de definición legibles por máquina que una herramienta aplica, en lugar de cambios manuales.
Configuration (configuración)
En Terraform, el conjunto de archivos .tf de un directorio que en conjunto describen la infraestructura deseada.
HCL
HashiCorp Configuration Language, el lenguaje declarativo en el que se escriben las configuraciones de Terraform.
Configuration drift (deriva de configuración)
Diferencias que se acumulan entre entornos, o entre el diseño registrado y la realidad, normalmente por cambios manuales no registrados.
ClickOps
Nombre informal para aprovisionar infraestructura a mano mediante una consola web.
Source of truth (fuente de verdad)
La única definición autorizada de cómo debe ser la infraestructura; en IaC, el código en control de versiones.
Repeatability (repetibilidad)
La capacidad de producir de nuevo la misma infraestructura a partir del mismo código y las mismas entradas.
Consistency (consistencia)
Los entornos construidos a partir de las mismas definiciones coinciden entre sí, lo que reduce las sorpresas de que algo funciona en staging pero no en producción.
Audit trail (rastro de auditoría)
El registro, proveniente del control de versiones y de los logs de la canalización, de quién cambió la infraestructura, cuándo y por qué.
CI/CD
Integración continua y entrega continua; canalizaciones automatizadas que prueban y despliegan cambios.
Pull request
Un cambio propuesto en el control de versiones que los compañeros revisan y aprueban antes de que se fusione.
Declarative (declarativo)
Describir el estado final deseado y dejar que la herramienta determine los pasos para alcanzarlo.
Imperative (imperativo)
Especificar la secuencia exacta de comandos o pasos a realizar.
Desired state (estado deseado)
La infraestructura descrita por la configuración, que Terraform intenta hacer realidad.
Dependency graph (grafo de dependencias)
El orden que Terraform construye a partir de las referencias y de depends_on, y que usa para decidir qué operaciones se ejecutan primero.
Provisioner
Una función de Terraform que ejecuta scripts o comandos durante la creación o destrucción de un recurso; se recomienda solo como último recurso.
Idempotence (idempotencia)
La propiedad de que repetir una operación produce el mismo resultado que hacerla una vez, sin cambios adicionales.
Drift (deriva)
Una diferencia entre la infraestructura real y lo que describen la configuración y el estado, normalmente por cambios manuales.
Refresh (actualización)
La parte de la planificación en la que Terraform lee del provider los atributos actuales de los objetos gestionados.
Perpetual diff (diff perpetuo)
Un cambio que aparece en cada plan porque un valor no es determinista o la API lo normaliza de forma diferente.
ignore_changes
Un ajuste de lifecycle que le indica a Terraform que no proponga actualizaciones cuando los argumentos listados difieren de la configuración.
Terraform core
El binario principal de Terraform, que analiza la configuración, construye el grafo de dependencias, gestiona el estado y dirige el flujo de trabajo.
Provider
Un plugin que permite a Terraform gestionar una plataforma o un servicio concreto traduciendo las solicitudes a llamadas a su API.
Plugin
Un ejecutable separado que core lanza y con el que se comunica por RPC; los providers son plugins.
Data source (origen de datos)
Una consulta de solo lectura, proporcionada por un provider, que obtiene información sobre objetos existentes.
RPC
Llamada a procedimiento remoto; el protocolo que usa Terraform core para enviar solicitudes a los plugins de los providers.
Multi-cloud (multinube)
Usar dos o más proveedores de nube pública a la vez.
Hybrid cloud (nube híbrida)
Combinar servicios de nube pública con infraestructura privada o local.
Native IaC tool (herramienta nativa de IaC)
La herramienta de aprovisionamiento propia de un proveedor de nube, como CloudFormation o las plantillas ARM, que solo gestiona los recursos de ese proveedor.
Cross-provider reference (referencia entre providers)
Una expresión en el recurso de un provider que usa un atributo del recurso de otro provider, lo que crea una dependencia implícita.
Provider alias (alias de provider)
Una segunda configuración del mismo provider, como otra región, que se selecciona en los recursos con el meta-argumento provider.
Service-agnostic (independiente del servicio)
Capaz de gestionar cualquier servicio que exponga una API, siempre que exista un provider para él.
Terraform Registry
El catálogo público donde se publican los providers y los módulos, y desde donde terraform init los descarga de forma predeterminada.
Utility provider (provider utilitario)
Un provider como random, local, tls o http que apoya a las configuraciones sin gestionar una plataforma de nube.
Branch protection (protección de ramas)
Reglas de una plataforma de Git, como exigir revisiones, que pueden codificarse con un provider de Git.
API
Interfaz de programación de aplicaciones; la interfaz programática que usa un provider para gestionar un servicio.
Provisioning (aprovisionamiento)
Crear y gestionar los propios recursos de infraestructura, como servidores y redes, normalmente mediante API.
Configuration management (gestión de configuración)
Instalar y mantener software y ajustes dentro de servidores existentes, como hacen Ansible, Chef, Puppet o Salt.
cloud-init / user_data
Un mecanismo para pasarle un script o una configuración de primer arranque a una máquina virtual nueva.
Tainted (contaminado)
Un recurso marcado para reemplazo, por ejemplo después de que falla un provisioner de tiempo de creación.
Immutable infrastructure (infraestructura inmutable)
Una práctica en la que los componentes desplegados nunca se modifican; los cambios se hacen reemplazándolos por versiones nuevas.
Mutable infrastructure (infraestructura mutable)
Servidores que se actualizan y parchean en el lugar durante toda su vida útil.
Snowflake server (servidor copo de nieve)
Un servidor cuya configuración se ha desviado hasta volverse única y difícil de reproducir.
Golden image (imagen de referencia)
Una imagen de máquina preconstruida y versionada que contiene el sistema operativo y el software, y que se usa para lanzar instancias idénticas.
create_before_destroy
Un ajuste de lifecycle que hace que Terraform cree el reemplazo antes de destruir el original.
-replace
Una opción de plan y apply que obliga a Terraform a reemplazar un recurso concreto aunque su configuración no haya cambiado.

Dominio 2: Terraform fundamentals (11%)

Consejos para el examen

  • Recuerda la división: required_version fija la CLI de Terraform; required_providers fija los providers. Ninguno acepta variables, porque el bloque terraform solo admite valores literales.
  • Si una pregunta muestra source = "hashicorp/aws" y pide la dirección completa, el hostname predeterminado oculto es registry.terraform.io.
  • Regla del límite superior para ~>: quita el último componente escrito y suma uno al nuevo último componente. ~> 2.1.3 significa < 2.2.0; ~> 2.1 significa < 3.0.
  • Archivo de bloqueo: haz commit de él. Directorio .terraform/: no hagas commit de él. Y el archivo de bloqueo cubre providers, no módulos.
  • Los providers los instala terraform init, no plan ni apply, y de forma predeterminada provienen del Terraform Registry público. Agregar o cambiar un provider siempre requiere volver a ejecutar init.
  • El namespace es la pista rápida: hashicorp/... significa official. Los providers partner los mantiene la empresa tecnológica dueña de la API; los community, personas o grupos.
  • La referencia es aws.west, no "aws.west" ni aws-west. Los recursos sin argumento provider usan la configuración predeterminada (sin alias).
  • No necesitas una configuración ni un comando separados por provider. Una sola configuración, un solo init y un solo apply pueden administrarlos todos, y las referencias entre ellos crean dependencias automáticamente.
  • Si te preguntan el propósito principal del estado, elige asociar los recursos de la configuración con objetos del mundo real. Los metadatos como las dependencias y la caché para el rendimiento son los otros propósitos enumerados.
  • sensitive = true oculta los valores de la salida, no del estado. La protección correcta para los secretos del estado es un backend seguro, cifrado y con control de acceso, además de valores efímeros o argumentos de solo escritura cuando estén disponibles.

Términos clave

terraform block (bloque terraform)
El bloque de nivel superior para los ajustes sobre el propio Terraform, como required_version, required_providers y backend.
required_version
Una restricción de versión que debe cumplir la CLI de Terraform en ejecución; si no la cumple, los comandos fallan.
terraform version
Comando que muestra la versión de Terraform instalada, la plataforma y, en un directorio inicializado, las versiones de los providers.
Version constraint (restricción de versión)
Una cadena con una o más condiciones, como >= 1.12.0, < 2.0.0, que una versión debe cumplir.
Pessimistic constraint (restricción pesimista, ~>)
Un operador que solo permite que aumente el componente de versión especificado más a la derecha, como ~> 1.12, que permite las versiones 1.x desde 1.12 en adelante.
required_providers
Bloque dentro de terraform que declara el nombre local, la dirección source y la restricción de versión de cada provider.
Source address (dirección source)
El identificador HOSTNAME/NAMESPACE/TYPE que le indica a Terraform de dónde descargar un provider.
Namespace
La parte de una dirección source que identifica a quien publica, como hashicorp o el nombre de una empresa o de un usuario.
Local name (nombre local)
El nombre de un provider específico del módulo, que se usa en los bloques provider y se compara con los prefijos de los tipos de recursos.
Dependency lock file (archivo de bloqueo de dependencias)
.terraform.lock.hcl, que registra las versiones de los providers y las sumas de verificación seleccionadas por terraform init.
Semantic versioning (versionado semántico)
Esquema de versiones MAJOR.MINOR.PATCH en el que los cambios major pueden romper la compatibilidad, minor agrega funciones y patch corrige bugs.
Pessimistic constraint (~>) (restricción pesimista)
Permite que solo aumente el componente de versión especificado más a la derecha, así que ~> 1.2 significa >= 1.2 y < 2.0.
Exact constraint (=) (restricción exacta)
Permite solo una versión específica; también es la única forma de seleccionar una versión preliminar.
Exclusion (!=) (exclusión)
Rechaza una versión específica y permite las demás que admitan las condiciones restantes.
terraform init -upgrade
Vuelve a seleccionar las versiones más nuevas de providers (y módulos) permitidas por las restricciones y actualiza el archivo de bloqueo.
Checksum (hash)
Huella digital de un paquete de provider que se usa para verificar que el archivo descargado es el esperado.
.terraform directory (directorio .terraform)
Directorio de trabajo local donde init guarda los providers y módulos descargados; no se incluye en commits.
terraform providers lock
Comando que agrega hashes de providers al archivo de bloqueo, incluso para otras plataformas con -platform.
Provider
Programa plugin que traduce las solicitudes de Terraform en llamadas a la API de una plataforma o servicio.
Provider schema (esquema del provider)
La definición que hace el provider de sus tipos de recursos, data sources, argumentos y atributos.
Plugin cache (caché de plugins)
Directorio compartido opcional donde init guarda los paquetes de providers para reutilizarlos entre directorios de trabajo.
Provider mirror (mirror de providers)
Copia local o de red de los paquetes de providers que se usa en lugar del registro público, por ejemplo en redes aisladas.
Computed attribute (atributo calculado)
Valor que establecen el provider o la plataforma después de la creación, como un ID, y no tu configuración.
Official provider (provider oficial)
Provider propiedad de HashiCorp y mantenido por HashiCorp, publicado bajo el namespace hashicorp.
Partner provider (provider de socio)
Provider escrito y mantenido por una empresa externa que forma parte del Technology Partner Program de HashiCorp, publicado bajo el namespace de la empresa.
Community provider (provider comunitario)
Provider publicado por personas o grupos de la comunidad, sin garantía de soporte de HashiCorp ni de un proveedor.
Archived provider (provider archivado)
Provider que ya no se mantiene y que sigue disponible para que las configuraciones existentes sigan funcionando.
Namespace (espacio de nombres)
La parte de la dirección de origen de un provider que corresponde a la organización o al usuario, como hashicorp en hashicorp/aws.
provider block (bloque provider)
Configuración de un provider, como la región, el endpoint o los ajustes de autenticación, que normalmente se coloca en el módulo raíz.
alias
Argumento que da nombre a una configuración adicional, no predeterminada, del mismo provider.
provider meta-argument (meta-argumento provider)
Argumento en un bloque resource o data, como provider = aws.west, que selecciona una configuración específica del provider.
Meta-argument (meta-argumento)
Argumento que maneja el propio Terraform y que puede usarse en cualquier tipo de recurso, como count, for_each, depends_on, provider y lifecycle.
providers map (mapa providers)
Argumento en un bloque module, como providers = { aws = aws.west }, que pasa configuraciones de provider a un módulo hijo.
configuration_aliases
Ajuste en la entrada de required_providers de un módulo que declara los nombres de configuraciones de provider adicionales que el módulo espera.
Resource type prefix (prefijo del tipo de recurso)
La parte de un tipo de recurso antes del primer guion bajo, como docker en docker_container, que selecciona el provider.
terraform providers
Comando que muestra los providers que requieren la configuración y sus módulos.
Dependency graph (grafo de dependencias)
El mapa interno de Terraform de qué objetos dependen de cuáles, que se usa para ordenar las operaciones en todos los providers.
Implicit dependency (dependencia implícita)
Dependencia que Terraform deduce de una referencia de un recurso a un atributo de otro recurso.
Partial apply (apply parcial)
Apply que se detiene después de que algunos cambios tienen éxito; el estado registra el trabajo completado para que la siguiente ejecución pueda continuar.
State (estado)
El registro de Terraform de los objetos reales que administra, sus atributos y metadatos, guardado en terraform.tfstate o en un backend remoto.
Resource address (dirección de recurso)
El identificador de un recurso en la configuración y el estado, como aws_instance.web o module.net.aws_vpc.main.
Backend
Dónde guarda Terraform el estado, como el disco local, HCP Terraform o un servicio de almacenamiento en la nube.
State locking (bloqueo del estado)
Mecanismo que impide que operaciones concurrentes escriban el mismo estado al mismo tiempo.
Drift (deriva)
Diferencia entre la infraestructura real y lo que esperan el estado y la configuración, normalmente causada por cambios hechos fuera de Terraform.
terraform.tfstate
El archivo de estado local predeterminado, un documento JSON que registra los recursos administrados y sus atributos.
sensitive (sensible)
Indicador en variables y outputs que oculta los valores en la salida de la CLI; los valores igual se guardan en el estado.
Ephemeral value (valor efímero)
Valor que existe solo durante una ejecución de Terraform y nunca se persiste en el estado ni en los archivos de plan.
Write-only argument (argumento de solo escritura)
Argumento de recurso cuyo valor Terraform envía al provider pero nunca guarda en el estado ni en el plan.
Serial and lineage (serial y lineage)
Metadatos del estado: el serial aumenta con cada escritura, y el lineage identifica el historial de un único estado.

Dominio 3: Core Terraform workflow (19%)

Consejos para el examen

  • Conoce el orden y el propósito: Write (código), Plan (previsualizar y revisar), Apply (aprovisionar). En los equipos, el plan se revisa junto con el código antes de aplicar nada.
  • -migrate-state mueve el estado al nuevo backend; -reconfigure no. -upgrade cambia las versiones de providers y módulos. Ninguna opción de init cambia la infraestructura real.
  • Validate no contacta las APIs de los providers ni el estado remoto, y no necesita valores de variables, pero sí necesita terraform init primero. Errores como un ID de imagen inexistente solo se detectan en plan o apply.
  • Memoriza los símbolos: + crear, - destruir, ~ actualizar en el lugar, -/+ reemplazar (destruyendo primero), +/- reemplazar (creando primero), <= leer. Plan nunca cambia la infraestructura, aunque sí hace refresh desde los providers. Para aplicar exactamente lo revisado, usa plan -out=FILE y luego apply FILE.
  • -refresh=false omite la revisión de la realidad; -refresh-only hace solo esa revisión y actualiza el estado. terraform refresh está obsoleto en favor de apply -refresh-only. -target es para uso excepcional, y en -var y -var-file gana el último valor de la línea de comandos.
  • Aplicar un archivo de plan guardado no pide aprobación y no acepta nuevas variables. Sin archivo de plan, apply pide confirmación a menos que se use -auto-approve, y solo la palabra exacta yes permite continuar. Apply no es transaccional: después de un fallo, los cambios completados quedan en el estado.
  • terraform destroy equivale a terraform apply -destroy. terraform plan -destroy solo previsualiza. Para eliminar un recurso en el trabajo normal, borra su bloque y aplica en lugar de usar destroy con -target. Destroy se ejecuta en orden inverso de dependencias y nunca toca recursos fuera de su estado.
  • fmt solo procesa el directorio actual a menos que agregues -recursive, y -check nunca escribe archivos. fmt comprueba el estilo, no la corrección, y no necesita init. Orden de menor a mayor costo: fmt, luego validate y luego plan.
  • Si una pregunta pide la forma recomendada de forzar la recreación de un recurso, elige terraform apply -replace=ADDRESS, no terraform taint, que está obsoleto. La marca automática de tainted todavía ocurre después de una creación o un provisioner fallidos, y untaint la quita.
  • El paralelismo tiene un valor predeterminado de 10 y cambia cuántas operaciones se ejecutan a la vez, nunca el orden. El orden viene del grafo: referencias implícitas más depends_on, invertido para destroy. terraform graph genera DOT para visualizarlo, y los ciclos son errores que se corrigen reestructurando.

Términos clave

Core workflow (flujo de trabajo central)
El ciclo Write, Plan y Apply de Terraform para cambiar la infraestructura.
Speculative plan (plan especulativo)
Plan que se ejecuta solo para revisión, como en un pull request, y que no puede aplicarse.
Remote backend (backend remoto)
Almacenamiento compartido del estado, como HCP Terraform, que permite a un equipo usar un solo estado de forma segura con bloqueo.
Pull request
Solicitud para fusionar cambios de código que permite a los compañeros revisarlos, a menudo con la salida del plan adjunta.
Saved plan (plan guardado)
Plan escrito en un archivo con terraform plan -out, que terraform apply puede ejecutar exactamente como se revisó.
terraform init
Comando que inicializa un directorio de trabajo: configura el backend e instala módulos y providers.
-migrate-state
Opción de init que copia el estado existente a un backend recién configurado.
-reconfigure
Opción de init que configura el backend desde cero, ignorando los ajustes guardados y sin migrar el estado.
Partial configuration (configuración parcial)
Dejar los ajustes del backend fuera del código y proporcionarlos con -backend-config en el momento de init.
-upgrade
Opción de init que selecciona las versiones más nuevas de providers y módulos permitidas por las restricciones y actualiza el archivo de bloqueo.
terraform validate
Comando que comprueba la sintaxis y la consistencia interna de la configuración sin contactar servicios remotos.
Internal consistency (consistencia interna)
Si las referencias, los nombres de argumentos, los tipos y los argumentos obligatorios de la configuración concuerdan entre sí y con los esquemas de los providers.
Provider schema (esquema del provider)
La lista del provider de tipos de recursos, argumentos y tipos, que validate necesita y que se obtiene con terraform init.
-json
Opción que muestra los resultados de la validación en un formato legible por máquina.
terraform fmt
Comando que reescribe la configuración con el estilo canónico; es una comprobación de estilo, no de validez.
Execution plan (plan de ejecución)
La vista previa de Terraform de las acciones de crear, actualizar, reemplazar y destruir necesarias para que la infraestructura real coincida con la configuración.
Refresh (actualización)
El paso del plan que pide a los providers los atributos actuales de los objetos gestionados para poder detectar el drift.
Drift (deriva)
Una diferencia entre la infraestructura real y el estado de Terraform causada por cambios hechos fuera de Terraform.
-/+ (replace, reemplazar)
Símbolo del plan que significa que el objeto existente se destruirá y se creará uno nuevo; +/- significa crear primero y luego destruir.
(known after apply)
Anotación del plan para valores que el provider solo determinará cuando se lleve a cabo el cambio.
-var / -var-file
Opciones que establecen valores de variables de entrada en la línea de comandos o desde un archivo; tienen la precedencia más alta y gana la última que se indique.
-target
Limita la planificación a recursos o módulos específicos y sus dependencias; pensado solo para uso excepcional y muestra una advertencia.
-refresh=false
Omite la consulta a los providers y planifica solo a partir del estado; es más rápido pero no ve el drift.
-refresh-only
Modo de plan o apply que actualiza el estado para que coincida con la infraestructura real sin cambiar esa infraestructura.
-replace
Fuerza en el plan el reemplazo de una instancia de recurso específica aunque su configuración no haya cambiado.
terraform apply
Comando que lleva a cabo un plan para crear, actualizar o destruir infraestructura y registra los resultados en el estado.
Interactive approval (aprobación interactiva)
El aviso que muestra apply sin archivo de plan; solo la palabra exacta yes permite continuar.
-auto-approve
Omite la confirmación interactiva yes; pensado para automatización con aprobación en otro lugar o para entornos desechables.
Stale plan (plan obsoleto)
Un plan guardado cuyo estado cambió desde que se creó; Terraform se niega a aplicarlo.
Tainted (marcado como dañado)
Marca en el estado para un recurso que se sabe dañado, como después de una creación fallida, de modo que se reemplazará.
terraform destroy
Comando que destruye todos los recursos gestionados por la configuración; es un alias de terraform apply -destroy.
plan -destroy
Crea un plan de destrucción para previsualizarlo, y opcionalmente guardarlo con -out, sin destruir nada.
Reverse dependency order (orden inverso de dependencias)
Destroy elimina los dependientes antes que los objetos de los que dependen, al revés del orden de creación.
prevent_destroy
Ajuste de lifecycle que hace fallar con un error cualquier plan que destruiría el recurso.
Orphaned resource (recurso huérfano)
Un objeto real que sigue existiendo pero que ya no está rastreado en ningún estado, por ejemplo después de eliminar un archivo de estado.
Canonical format (formato canónico)
La disposición estándar de HashiCorp para los archivos de Terraform, que incluye sangría de dos espacios y signos igual alineados.
-check
Opción de fmt que informa los archivos sin formato y termina con un código distinto de cero sin modificarlos.
-diff
Opción de fmt que muestra las diferencias de formato.
-recursive
Opción de fmt que también procesa los archivos de los subdirectorios.
terraform taint
Comando obsoleto que marcaba un recurso en el estado para reemplazarlo en el siguiente apply.
terraform untaint
Comando que quita la marca de tainted de un recurso en el estado.

Dominio 4: Terraform configuration (22%)

Consejos para el examen

  • Los data sources se direccionan con el prefijo data. y Terraform nunca los destruye. Si una pregunta del examen pide cómo usar un objeto existente que Terraform no debe gestionar, la respuesta es un data source. Las instancias usan [0] con count y ["key"] con for_each.
  • Terraform ordena las operaciones usando referencias, no el orden de los archivos. Si una pregunta pide cómo sabe Terraform que debe crear la red antes que la subred, la respuesta es la dependencia implícita de aws_vpc.main.id. Usa depends_on solo para dependencias que ninguna referencia puede expresar.
  • Precedencia de menor a mayor: variables de entorno TF_VAR_, terraform.tfvars, terraform.tfvars.json, *.auto.tfvars en orden léxico, y luego -var y -var-file. Los archivos que no siguen esos patrones de nombre solo se cargan mediante -var-file. sensitive oculta la salida, pero no protege el estado.
  • El bloque es locals, pero la referencia es local.name. Los valores de un módulo hijo solo son accesibles mediante outputs, como module.NAME.OUTPUT_NAME. Los outputs sensibles se ocultan en los listados normales, pero terraform output -raw y -json los imprimen, y siempre están en el estado.
  • Las listas son ordenadas e indexadas; los sets no tienen orden y son únicos; los mapas tienen claves de tipo cadena y un solo tipo de valor. Los objetos y las tuplas son las versiones estructurales que permiten tipos mixtos. for_each necesita un mapa o un set, así que convierte las listas con toset().
  • Aprende qué produce cada tipo de corchete: [for ...] da una lista o tupla, {for ... : k => v} da un mapa u objeto. El splat funciona con listas, no con mapas, y dynamic genera bloques anidados, no recursos.
  • Terraform no admite funciones definidas por el usuario en HCL. Para probar el comportamiento de una función, usa terraform console, que evalúa expresiones sin modificar la infraestructura.
  • for_each acepta mapas y sets de cadenas, no listas, y da claves estables. Los índices de count se desplazan cuando se quitan elementos del medio. No puedes usar ambos en un mismo bloque.
  • Usa depends_on solo para dependencias ocultas. Recuerda que prevent_destroy no impide la destrucción si se elimina el bloque de recurso completo, y que los valores de lifecycle deben ser literales, no variables.
  • Recuerda la severidad: los fallos de validation, precondition y postcondition son errores que detienen la ejecución, mientras que un assert fallido en un bloque check es solo una advertencia.
  • La trampa favorita del examen: sensitive solo oculta los valores en la salida de la CLI. No los cifra ni los mantiene fuera del archivo de estado.
  • Los secretos leídos de Vault mediante un data source normal acaban en el estado de Terraform. Vault no cambia eso; protege el estado y prefiere secretos de corta duración o efímeros.

Dominio 5: Terraform modules (11%)

Consejos para el examen

  • Si una pregunta te pide qué convierte un directorio en módulo, la respuesta es simplemente que contiene archivos de configuración de Terraform; el módulo raíz es aquel desde el que ejecutas los comandos.
  • Conoce las formas de las direcciones: ./ o ../ significa local, tres partes separadas por barras significan registro público, un nombre de host más tres partes significa registro privado, y git:: o ?ref= significa un origen Git.
  • Los argumentos de un bloque module (salvo los meta-argumentos) se corresponden uno a uno con los bloques variable del hijo; tanto una variable obligatoria que falta como un argumento no declarado son errores.
  • Los valores bajan solo mediante argumentos del bloque module y suben solo mediante outputs; un hijo nunca puede leer directamente los valores var. del padre, y solo los outputs raíz aparecen en terraform output.
  • Las configuraciones de provider predeterminadas se heredan automáticamente; las que tienen alias nunca se heredan y deben pasarse con el mapa providers en el bloque module, usando como clave el nombre de provider del hijo.
  • version es solo para módulos de registro; los módulos Git se fijan con ?ref= (una etiqueta o un SHA es más seguro que una rama). Recuerda también que el archivo de bloqueo no fija las versiones de los módulos.
  • Agregar o cambiar el origen o la versión de un módulo requiere init (o get); cambiar solo los valores de entrada del módulo no. Nunca confirmes el directorio .terraform en el repositorio, pero sí confirma .terraform.lock.hcl.
  • Prefiere for_each sobre count cuando las instancias son distintas y podrían quitarse de forma individual; los índices de count se desplazan cuando se quita un elemento del medio. Usa count = condición ? 1 : 0 para que un módulo sea opcional.
  • Los nombres de archivo son una convención, no un requisito: Terraform combina todos los archivos .tf de un directorio, pero la estructura estándar (main, variables, outputs, README) es lo que esperan el registro y los revisores.

Dominio 6: Terraform state management (11%)

Consejos para el examen

  • Si no hay bloque backend, se usa el backend local, que escribe terraform.tfstate y un terraform.tfstate.backup de un solo paso en el directorio de trabajo. Mantén ambos fuera de Git.
  • El bloqueo es automático en los backends que lo admiten. force-unlock necesita el ID del bloqueo y es un último recurso; -lock-timeout espera un bloqueo en lugar de fallar de inmediato.
  • El bloque backend va dentro de terraform {}, solo en el módulo raíz, y cualquier cambio en él requiere volver a ejecutar terraform init. HCP Terraform usa un bloque cloud en su lugar.
  • Si una pregunta muestra var. dentro de un bloque backend, la respuesta es que no está permitido; usa en su lugar archivos -backend-config o pares clave/valor en init, y mantén los secretos en variables de entorno.
  • Para que tus recursos sigan registrados al cambiar de backend, usa -migrate-state; -reconfigure empieza desde cero con el nuevo backend y no copia nada. Haz un respaldo antes y ejecuta plan después.
  • El bloque cloud y un bloque backend son mutuamente excluyentes; el bloque cloud selecciona workspaces por name (uno) o por tags (varios), no puede usar variables y se puede sobrescribir con TF_CLOUD_ORGANIZATION y TF_WORKSPACE.
  • sensitive = true no es cifrado. Protege el estado con un backend remoto cifrado, con acceso controlado y versionado, mantenlo fuera del control de versiones y, cuando puedas, mantén los secretos fuera del estado.
  • apply -refresh-only solo actualiza el estado y nunca cambia la infraestructura; para conservar un cambio manual de forma permanente también debes actualizar la configuración.
  • Los workspaces de la CLI solo separan el estado, no las credenciales ni los backends; sirven para copias de corta duración y no se recomiendan como barrera de aislamiento para entornos de producción.

Un bloque como backend "s3" {} que nombra el tipo de backend y deja todos los argumentos para init.

-force-copy
Un indicador de init que responde automáticamente que sí a las preguntas de migración del estado.

Muestra el estado actual desde el backend configurado; útil para hacer un respaldo antes de una migración.

Mover el estado de un backend a otro, como de local a s3 o de s3 a HCP Terraform, sin cambiar la infraestructura real.
organization
El argumento del bloque cloud que nombra la organización de HCP Terraform dueña de los workspaces.

El bloque anidado que asocia la configuración a un workspace por nombre o a varios por etiquetas.
Execution mode (modo de ejecución)
Un ajuste del workspace que decide si las ejecuciones se hacen de forma remota en HCP Terraform, localmente en tu máquina o en agentes autoalojados.
terraform login
Un comando que obtiene un token de API de HCP Terraform y lo guarda en un archivo local de credenciales para que lo use la CLI.
TF_CLOUD_ORGANIZATION / TF_WORKSPACE
Variables de entorno que proporcionan o sobrescriben la organización y el workspace que usa el bloque cloud.
Secrets in state (secretos en el estado)
El hecho de que Terraform guarda en el estado los atributos de los recursos, incluidas contraseñas y claves, en texto plano.
sensitive
Un ajuste de variables y outputs que oculta los valores en la salida de la CLI, pero no los cifra ni los elimina del estado.
Encryption at rest (cifrado en reposo)
La protección del estado almacenado por parte del servicio de almacenamiento del backend, como el cifrado del lado del servidor de S3 con encrypt = true y una clave KMS opcional.
Access control (control de acceso)
Permisos de IAM o de la plataforma que restringen quién puede leer o escribir el almacenamiento del estado.
terraform_remote_state
Un data source que lee los outputs raíz del estado de otra configuración, lo que requiere acceso de lectura a todo ese estado.
Ephemeral values and write-only arguments (valores efímeros y argumentos de solo escritura)
Funciones que permiten a Terraform usar un secreto durante una ejecución sin guardarlo en el estado ni en los archivos de plan.

Una diferencia entre la infraestructura real y el estado que Terraform registró por última vez, normalmente por cambios hechos fuera de Terraform.

El paso en el que Terraform lee de los providers los ajustes actuales de los objetos administrados antes de planificar.
-refresh-only
Un modo de plan o apply que solo actualiza el estado para que coincida con la infraestructura real, sin cambiar ningún recurso.

El comando obsoleto que actualizaba el estado de inmediato sin mostrar los cambios ni pedir aprobación.
ignore_changes
Un ajuste de lifecycle que le indica a Terraform que ignore los cambios en atributos específicos al planificar.

default workspace (workspace default)
El workspace en el que empieza toda configuración; no se puede eliminar.
terraform.workspace
Una expresión que devuelve el nombre del workspace actual para usarlo en la configuración.
terraform.tfstate.d
El directorio donde el backend local guarda el estado de los workspaces que no son default.

Una forma del comando select que cambia a un workspace y lo crea primero si no existe.

Dominio 7: Maintain infrastructure with Terraform (8%)

Consejos para el examen

  • Los bloques import se revisan en el plan y se aplican como cualquier otro cambio; -generate-config-out escribe HCL inicial en un archivo que no debe existir previamente, y un plan de importación limpio muestra solo importaciones.
  • terraform import necesita que el bloque resource exista primero, importa un objeto a la vez, escribe en el estado de inmediato y no genera configuración; los bloques import eliminan esos límites.
  • state list da direcciones, state show da los atributos de un recurso, show da todo (o un archivo de plan) y output da solo los outputs raíz.
  • Renombrar un recurso sin moved ni state mv hace que Terraform planifique destruir y crear; moved es la opción declarativa y revisable, y funciona automáticamente en todos los entornos.
  • Eliminar solo un bloque resource significa destruir. Para dejar de administrar sin eliminar, usa un bloque removed con destroy = false o terraform state rm, y quita el bloque resource.
  • TRACE es el nivel más detallado, JSON produce logs de nivel TRACE en formato JSON, y TF_LOG_PATH agrega al final de un archivo y no hace nada a menos que haya un nivel de log definido.
  • Usa los logs para errores de provider y fallos; reporta los fallos de core a Terraform y los de un provider a ese provider; incluye en los reportes de bugs la salida de terraform version, una configuración mínima y un log TRACE censurado.
  • terraform output -json muestra los valores sensibles en texto plano y es la forma de exportar listas y mapas; -raw sirve para valores primitivos individuales. terraform graph produce DOT, que renderizas con Graphviz.

Términos clave

import block (bloque import)
Un bloque declarativo con to e id que le indica a Terraform que ponga un objeto existente bajo una dirección de recurso durante plan y apply.
Import ID (ID de importación)
El identificador de un objeto existente específico del provider, como un ID de instancia o el nombre de un bucket, documentado en la página de cada recurso.
-generate-config-out
Un indicador de terraform plan que escribe el HCL generado para los destinos de importación que no tienen bloques resource en un archivo nuevo que no debe existir previamente.
Adopting infrastructure (adoptar infraestructura)
Poner recursos creados manualmente bajo la administración de Terraform sin recrearlos.
for_each in import blocks (for_each en bloques import)
Una forma de importar un conjunto de objetos similares, como muchos buckets, con un solo bloque import.
terraform import
Un comando de la CLI que escribe de inmediato un objeto existente en el estado en una dirección de recurso dada.

La dirección del recurso en la configuración a la que se vinculará el objeto importado, como aws_instance.web o module.app.aws_instance.web[0].

El identificador del objeto real específico del provider, en el formato documentado para ese tipo de recurso.

El bloque resource que ya debe existir en la configuración para que terraform import tenga éxito.
Post-import plan (plan posterior a la importación)
Ejecutar terraform plan después de importar y ajustar la configuración hasta que no se muestren cambios.
terraform state list
Enumera las direcciones de todos los recursos del estado, opcionalmente filtradas por un prefijo de dirección o por -id.
terraform state show
Muestra todos los atributos registrados de una instancia de recurso en el estado, con los valores sensibles ocultos.

Muestra todo el estado, o un archivo de plan guardado, en forma legible o en JSON.
terraform output
Imprime los valores de output del módulo raíz desde el estado, con las opciones -json y -raw para scripts.
-raw
Un indicador de terraform output que imprime un solo valor de cadena sin comillas ni formato.
moved block (bloque moved)
Un bloque de configuración con from y to que registra un cambio de dirección para que Terraform actualice el estado en lugar de reemplazar el objeto.

Un comando de la CLI que cambia de inmediato la dirección de un objeto en el estado, con -dry-run para previsualizar.

Reestructurar la configuración (renombrar, mover a módulos, agregar count o for_each) sin cambiar la infraestructura real.

El identificador que usa Terraform para rastrear un objeto, como module.app.aws_instance.web[0].

Lo que propone Terraform cuando cambia una dirección y ningún bloque moved ni state mv le indica que el objeto solo se movió.

Un bloque de configuración que le dice a Terraform que deje de administrar una dirección, destruyéndola o no según el destroy de lifecycle.

El ajuste de lifecycle del bloque removed que elimina el objeto del estado dejando la infraestructura real en su lugar.

Un comando de la CLI que elimina de inmediato la entrada de un recurso del estado sin afectar al objeto real, con -dry-run para previsualizar.

Un objeto real que existe pero no está registrado en ningún estado de Terraform.
Ownership transfer (transferencia de propiedad)
Trasladar la administración de un objeto de una configuración a otra eliminándolo de un estado e importándolo en otro.

Variable de entorno que escribe (agregando al final) la salida de los logs en un archivo en lugar de en la salida de error estándar; necesita que haya un nivel de log definido.

Variable de entorno que define el nivel de log solo para los plugins de los providers.

Un valor de TF_LOG que produce logs con nivel TRACE en formato JSON legible por máquinas.

Comando que muestra la versión de Terraform y las versiones de los providers instalados, necesarias para los reportes de bugs.

La configuración más pequeña que todavía muestra el problema, incluida en un reporte de bug.

Los cuatro lugares donde suelen estar los problemas: lenguaje, estado, core y provider.

Un lenguaje de descripción de grafos y el conjunto de herramientas de código abierto, que incluye el comando dot, que lo convierte en una imagen.

Dominio 8: HCP Terraform (10%)

Consejos para el examen

  • Terraform Cloud se renombró como HCP Terraform; Terraform Enterprise es la versión autoalojada. No memorices precios ni límites; debes saber que las funciones centrales del flujo de trabajo son gratuitas para empezar y que las funciones de gobernanza están en los niveles de pago.
  • terraform login guarda un token en credentials.tfrc.json; en CI usa TF_TOKEN_<host> con los puntos reemplazados por guiones bajos. En el bloque cloud, workspaces usa name (uno) o tags (varios), nunca ambos, y terraform init lo activa.
  • En el flujo de trabajo VCS, los pull requests disparan ejecuciones especulativas (solo de plan); los merges a la rama rastreada disparan ejecuciones reales. Los workspaces conectados a VCS rechazan los applies desde la CLI pero permiten planes especulativos desde la CLI. Basado en la API significa versiones de configuración subidas por tus propias herramientas.
  • Los workspaces de HCP Terraform son entornos completos con permisos separados (estado, variables, ejecuciones, ajustes, acceso); los workspaces de la CLI solo separan el estado dentro de un backend.
  • Jerarquía: la organización contiene proyectos y los proyectos contienen workspaces; cada workspace está exactamente en un proyecto, y el acceso de equipos a nivel de proyecto cubre todos sus workspaces actuales y futuros.
  • Las credenciales de los providers van en variables de entorno, no en variables de Terraform. Las variables sensibles son de solo escritura. Las variables del workspace ganan a los variable sets normales; los variable sets prioritarios ganan a los valores del workspace.
  • Las verificaciones de políticas se ejecutan después del plan y antes del apply. Niveles de Sentinel: advisory advierte, soft-mandatory puede anularlo un usuario autorizado y hard-mandatory no se puede anular. OPA usa advisory y mandatory.
  • Las evaluaciones de estado solo detectan e informan; nunca cambian la infraestructura ni el estado. La detección de drift equivale a un plan refresh-only programado; la validación continua vuelve a comprobar los bloques check y las precondiciones y poscondiciones.
  • Asocia la función: los proveedores de VCS conectan repositorios, los run triggers encadenan workspaces después de un apply exitoso, los run tasks llaman a verificaciones externas que pueden bloquear, las notificaciones envían alertas que no pueden bloquear y las credenciales dinámicas de providers reemplazan las claves estáticas de la nube por credenciales OIDC por ejecución.
