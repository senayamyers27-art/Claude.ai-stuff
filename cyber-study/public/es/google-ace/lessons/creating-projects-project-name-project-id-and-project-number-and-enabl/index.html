Creación de proyectos: nombre, ID y número del proyecto, y habilitación de APIs

Antes de construir cualquier cosa necesitas un proyecto. Puedes crear uno en la consola desde el selector de proyectos eligiendo New project, o desde la línea de comandos con gcloud projects create PROJECT_ID --name="Display name" --folder=FOLDER_ID. Puedes usar --organization=ORG_ID en lugar de --folder para ubicarlo directamente bajo la organización. Crear proyectos requiere el rol Project Creator en la organización o carpeta donde vivirá el proyecto, y el proyecto debe estar vinculado a una cuenta de facturación antes de poder usar la mayoría de los servicios de pago. Un proyecto recién creado sin vínculo de facturación puede existir, pero intentar crear una VM en él fallará con un error de facturación.

Cada proyecto tiene tres identificadores, y a las preguntas del examen les gusta evaluar la diferencia. El nombre del proyecto es una etiqueta visible y amigable. Puedes cambiarlo en cualquier momento, no necesita ser único, y dos equipos pueden tener cada uno un proyecto llamado Sandbox. El ID del proyecto es una cadena única a nivel global, formada por letras minúsculas, dígitos y guiones, que eliges (o aceptas una generada) al crear el proyecto. Debe empezar con una letra y tener entre 6 y 30 caracteres. Nunca se puede cambiar, y es lo que usan gcloud, las APIs, el código de Terraform y muchos nombres de recursos. El número del proyecto lo asigna Google, también es permanente y aparece en lugares como la cuenta de servicio predeterminada de Compute Engine, PROJECT_NUMBER-compute@developer.gserviceaccount.com.

Como el ID del proyecto es permanente y único a nivel global, elígelo con cuidado. Una buena convención incluye el equipo o la aplicación y el entorno, como payroll-prod o shop-dev, a veces con un sufijo corto cuando alguien más en el mundo ya tomó el ID obvio. Si un equipo decide después que el ID está mal, la única forma de obtener un ID diferente es crear un proyecto nuevo y mover las cargas de trabajo. En cambio, cambiar el nombre visible es un cambio inofensivo que no afecta a los scripts, porque los scripts hacen referencia al ID.

Los servicios de Google Cloud se exponen como APIs, y la mayoría están deshabilitadas en un proyecto nuevo. Si intentas usar un servicio cuya API está apagada, recibes un error que te dice que la API no se ha usado antes en el proyecto o que está deshabilitada, normalmente con un enlace para habilitarla. No es un problema de permisos, y otorgar más roles de administración de identidades y accesos (IAM) no lo resolverá. Habilitas la API en la página APIs and services de la consola o con gcloud services enable compute.googleapis.com, y el mismo patrón funciona para run.googleapis.com, container.googleapis.com, sqladmin.googleapis.com, etcétera. gcloud services list --enabled muestra lo que está activado, y gcloud services list --available muestra lo que podrías activar.

Habilitar una API no cuesta nada por sí mismo. Pagas por los recursos que luego creas y el uso que generas. Habilitar sí requiere un permiso, serviceusage.services.enable, que incluyen roles como Owner, Editor y Service Usage Admin. Algunos comandos de gcloud ofrecen habilitar una API por ti la primera vez que usas un servicio, lo cual es cómodo, pero también explica por qué el script de un compañero puede funcionar en su proyecto y fallar en el tuyo. Recuerda que las APIs habilitadas son por proyecto: activar Cloud Run en shop-dev no hace nada por shop-prod, así que la automatización que crea proyectos normalmente habilita las APIs necesarias como uno de sus primeros pasos.

Habilitar algunas APIs también crea cuentas de servicio administradas por Google, llamadas agentes de servicio (service agents), que permiten que el servicio actúe en tu proyecto, por ejemplo para conectar discos, descargar imágenes de contenedor o escribir registros. Tienen direcciones de correo que normalmente incluyen el número del proyecto y un dominio propiedad de Google, y aparecen en la página de IAM cuando marcas la opción para incluir las asignaciones de roles proporcionadas por Google. No las elimines ni les quites sus roles, o el servicio dejará de funcionar de formas confusas.

Cuando ya no necesitas un proyecto, ciérralo con gcloud projects delete PROJECT_ID o desde la página Manage resources de la consola. El proyecto entra en un período de eliminación pendiente de aproximadamente 30 días, durante el cual la facturación se detiene y los recursos se apagan, y un Owner puede restaurarlo con gcloud projects undelete PROJECT_ID. Después de ese período se elimina definitivamente, y nadie puede volver a usar su ID de proyecto. Eliminar un proyecto es la forma más limpia de asegurarte de que nada en él siga costando dinero, y por eso los entornos de prueba de corta duración suelen crearse como proyectos separados.

Términos clave

Project ID (ID del proyecto)
El identificador permanente y único a nivel global que eliges al crear el proyecto y que usas en comandos y APIs.
Project number (número del proyecto)
Un identificador numérico permanente que asigna Google y que se usa en algunos nombres de cuentas de servicio.
Project name (nombre del proyecto)
Una etiqueta visible que se puede cambiar y que no necesita ser única.
Service agent (agente de servicio)
Una cuenta de servicio administrada por Google que un servicio de Google Cloud usa para actuar sobre los recursos de tu proyecto.
Project Creator
El rol de IAM, otorgado en una organización o carpeta, que permite crear proyectos allí.
gcloud services enable
El comando que activa una API, como run.googleapis.com, en el proyecto actual.
Ejemplo real

Una desarrolladora crea un proyecto con el ID shop-dev-4821 y el nombre Shop Dev. Cuando ejecuta gcloud run deploy, gcloud ofrece habilitar la Cloud Run API. Más tarde el equipo cambia el nombre del proyecto a Shop Development en la consola; todos los scripts siguen funcionando porque hacen referencia al ID del proyecto, que no cambió.

Consejo para el examen: Si una pregunta dice que el equipo quiere cambiar un ID de proyecto, la respuesta es que no se puede; solo el nombre visible puede cambiar. Un error de 'API no habilitada' se resuelve habilitando la API, no otorgando más roles de IAM.

Comprueba lo que sabes

¿Qué identificador del proyecto aparece en la dirección de correo de la cuenta de servicio predeterminada de Compute Engine?

El número del proyecto, como en PROJECT_NUMBER-compute@developer.gserviceaccount.com.

¿Cómo listas las APIs habilitadas en el proyecto actual?

Ejecuta gcloud services list --enabled, o revisa APIs and services en la consola.

¿Qué rol necesitas en una carpeta para crear proyectos en ella?

Project Creator.
