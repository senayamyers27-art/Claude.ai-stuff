ISC2 Certified Cloud Security Professional 2026 outline (effective Aug 1, 2026)

Arquitectura de referencia de la nube: modelos de servicio IaaS, PaaS y SaaS y capacidades del servicio de nube

Una arquitectura de referencia es un mapa compartido de las partes de un servicio de nube y de quién opera cada una. El examen Certified Cloud Security Professional (CCSP) la usa para comprobar si sabes qué controla el cliente en cada modelo de servicio. Eso importa porque el control decide la responsabilidad: las partes que controlas son las que debes proteger, mientras que las partes que controla el proveedor son las que solo puedes solicitar, negociar en un contrato o verificar mediante evidencia.

Ayuda imaginar la pila de abajo hacia arriba: el centro de datos físico con su energía y refrigeración, los servidores y el hardware de red, el hipervisor que crea las máquinas virtuales, el sistema operativo invitado, el middleware y los entornos de ejecución, la aplicación y, por último, los datos y los usuarios que acceden a ellos. Cada modelo de servicio traza una línea en algún punto de esa pila. Lo que está debajo de la línea pertenece al proveedor; lo que está encima pertenece al cliente.

Infrastructure as a Service (IaaS, infraestructura como servicio) traza la línea abajo. El cliente recibe máquinas virtuales, redes virtuales y almacenamiento. El proveedor opera el centro de datos físico, el hardware y el hipervisor. El cliente instala y parchea el sistema operativo invitado, el middleware y las aplicaciones, configura firewalls virtuales y reglas de red, y administra las identidades y los datos. En la consola de un proveedor verías al cliente eligiendo una imagen de máquina, dimensionando la instancia, conectando discos y escribiendo reglas de grupos de seguridad, y todas son decisiones del cliente con consecuencias para el cliente.

Platform as a Service (PaaS, plataforma como servicio) sube la línea. Ahora el proveedor opera el sistema operativo y el entorno de ejecución, además de todo lo que está debajo. Despliegas código en una plataforma de aplicaciones o usas una base de datos administrada, y el proveedor parchea la plataforma subyacente. El cliente sigue siendo responsable del código de su aplicación, de sus decisiones de configuración, como si una base de datos acepta conexiones desde internet, de sus identidades y derechos de acceso, y de sus datos. PaaS elimina una gran carga de parches, pero también quita visibilidad; no puedes instalar tu propio agente en el host subyacente, así que dependes de los registros y los informes de aseguramiento del proveedor.

Software as a Service (SaaS, software como servicio) traza la línea casi en la parte superior. El proveedor entrega una aplicación terminada y opera todo lo necesario para que siga funcionando. El cliente controla principalmente sus usuarios y sus permisos, opciones de configuración como el uso compartido externo y la retención, y los datos que introduce. Esos pocos controles del cliente siguen importando mucho; muchas filtraciones de datos en SaaS provienen de una opción de uso compartido o de una cuenta con demasiados privilegios, y no de una falla en el software del proveedor.

ISO/IEC 17788, la norma internacional de vocabulario de la nube, describe la misma idea como tipos de capacidad de nube. El tipo de capacidad de infraestructura permite al cliente aprovisionar y usar recursos de procesamiento, almacenamiento o red, lo que corresponde a IaaS. El tipo de capacidad de plataforma permite al cliente desplegar, administrar y ejecutar aplicaciones creadas o adquiridas por él usando lenguajes y herramientas que el proveedor admite, lo que corresponde a PaaS. El tipo de capacidad de aplicación permite al cliente usar las aplicaciones del proveedor, lo que corresponde a SaaS. Categorías de servicio con nombre propio, como cómputo como servicio, almacenamiento de datos como servicio, red como servicio y comunicaciones como servicio, encajan dentro de estos tipos de capacidad. Espera preguntas de examen que usen la redacción de ISO en lugar de las siglas conocidas.

El patrón que debes recordar es que, al pasar de IaaS a PaaS y a SaaS, el cliente cede control y gana comodidad. Menos control significa que el cliente depende más de los contratos, los acuerdos de nivel de servicio (SLA) y el aseguramiento independiente, como los informes de auditoría, para confirmar que los controles del proveedor existen y funcionan. Más control significa más trabajo: un cliente de IaaS puede endurecer sus servidores exactamente como quiera, pero también debe parchearlos, monitorearlos y responder cuando los atacan.

Algunas responsabilidades nunca se mueven, sea cual sea el modelo. En todos los casos el cliente es dueño de sus datos, los clasifica, decide quién tiene acceso y rinde cuentas ante los reguladores y sus propios clientes si esos datos se manejan mal. Un buen hábito es construir una matriz de responsabilidades sencilla para cada servicio que uses, listando cada capa de la pila y marcándola como del proveedor, del cliente o compartida. Eso convierte un modelo vago en una lista de verificación con la que tu equipo puede actuar cuando se anuncie el próximo parche urgente. Revísala cada vez que adoptes un servicio nuevo o un proveedor cambie lo que incluye un servicio.

Términos clave

IaaS
Infrastructure as a Service (infraestructura como servicio): el cliente alquila cómputo, almacenamiento y redes virtuales y administra todo desde el sistema operativo invitado hacia arriba.
PaaS
Platform as a Service (plataforma como servicio): el proveedor opera el sistema operativo y el entorno de ejecución, y el cliente despliega y administra sus propias aplicaciones, configuración y datos.
SaaS
Software as a Service (software como servicio): el proveedor entrega una aplicación completa y el cliente administra usuarios, configuración y datos.
Tipo de capacidad de nube (cloud capability type)
La clasificación de ISO/IEC 17788 de lo que un servicio ofrece al cliente: capacidad de infraestructura, de plataforma o de aplicación.
Acuerdo de nivel de servicio (SLA)
El compromiso contractual de un proveedor sobre niveles de servicio medibles, como la disponibilidad y el tiempo de respuesta del soporte.
Ejemplo real

Una startup ejecuta su aplicación web en un PaaS administrado, guarda archivos en almacenamiento de objetos y usa una suite de correo SaaS. Cuando se anuncia una falla crítica del kernel, la startup no hace nada en las partes PaaS y SaaS porque los proveedores las parchean, pero sí debe parchear las dos máquinas virtuales IaaS que opera para una herramienta de informes heredada. También revisa la configuración de uso compartido del SaaS, porque un parche no arregla una carpeta mal configurada.

Consejo para el examen: Cuando una pregunta te pide quién parchea el sistema operativo, la respuesta depende del modelo: el cliente en IaaS y el proveedor en PaaS y SaaS. Los datos y las decisiones de acceso quedan en el cliente en los tres. Fíjate en los nombres de los tipos de capacidad de ISO/IEC 17788 usados en lugar de IaaS, PaaS y SaaS.

Comprueba lo que sabes

En PaaS, ¿quién es responsable de parchear el entorno de ejecución y el sistema operativo?

El proveedor; el cliente es responsable del código de su aplicación, su configuración y sus datos.

¿Qué modelo de servicio le da al cliente más control y, por lo tanto, más responsabilidad de seguridad?

IaaS, porque el cliente administra el sistema operativo invitado y todo lo que está encima.

¿Qué describe el tipo de capacidad de aplicación?

Un servicio en el que el cliente usa las aplicaciones del proveedor, lo que corresponde a SaaS.

Nombra una responsabilidad que queda en el cliente por igual en IaaS, PaaS y SaaS.

La propiedad y la protección de sus datos, incluida la decisión de quién puede acceder a ellos.
