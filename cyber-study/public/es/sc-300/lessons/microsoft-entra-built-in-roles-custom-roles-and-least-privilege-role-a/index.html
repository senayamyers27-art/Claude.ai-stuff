Microsoft Certified: Identity and Access Administrator Associate SC-300 (skills outline of April 27, 2026)

Roles integrados y personalizados de Microsoft Entra, y asignación de roles con mínimo privilegio

Los roles de Microsoft Entra controlan quién puede administrar el directorio en sí: usuarios, grupos, aplicaciones, configuración de autenticación y objetos de identidad similares. Son distintos de los roles de control de acceso basado en roles (RBAC) de Azure, como Owner, Contributor o Reader, que controlan recursos de Azure como máquinas virtuales, cuentas de almacenamiento y suscripciones. Un Global Administrator no administra automáticamente los recursos de Azure, y el Owner de una suscripción no puede restablecer la contraseña de un usuario por tener ese rol. Confundir ambos sistemas es una trampa clásica del examen, así que ten presente una pregunta en cada escenario: ¿el administrador gestiona objetos de identidad o recursos de Azure?

Microsoft ofrece muchos roles integrados de Entra, cada uno con un conjunto fijo de permisos que no puedes editar. Global Administrator puede hacer casi todo y debería ser escaso; Microsoft recomienda menos de cinco por tenant, además de cuentas de acceso de emergencia separadas. Privileged Role Administrator administra las asignaciones de roles y Privileged Identity Management (PIM), así que en la práctica es un camino hacia cualquier otro rol y merece el mismo cuidado. User Administrator crea y administra usuarios y grupos, y puede restablecer las contraseñas de muchos usuarios, pero no de todos. Helpdesk Administrator restablece las contraseñas de quienes no son administradores y de algunos roles limitados, y Password Administrator es una opción aún más limitada, centrada en el restablecimiento de contraseñas.

Los roles de autenticación son una comparación frecuente. Authentication Administrator puede ver y administrar métodos de autenticación, como números de teléfono, y exigir que un usuario vuelva a registrar la autenticación multifactor (MFA), para usuarios que no son administradores. Privileged Authentication Administrator puede hacer lo mismo para cualquier usuario, incluidos los Global Administrators. Esa diferencia importa porque cambiar el número de teléfono de MFA de un administrador es una maniobra clásica de toma de control de cuentas, así que se reserva para el rol de mayor confianza.

Varios otros roles integrados aparecen en los escenarios. Security Administrator administra las funciones de seguridad y lee los informes de seguridad. Conditional Access Administrator administra las directivas de Conditional Access. Groups Administrator administra los grupos y su configuración, y License Administrator administra las asignaciones de licencias. Application Administrator administra los registros de aplicaciones, las aplicaciones empresariales y application proxy, mientras que Cloud Application Administrator hace lo mismo pero sin derechos sobre application proxy. Global Reader puede ver casi todo lo que ve un Global Administrator pero no puede cambiar nada, lo que lo hace adecuado para auditores y para administradores que sobre todo necesitan mirar antes de actuar.

Los roles personalizados te permiten construir un rol a partir de permisos individuales cuando ningún rol integrado se ajusta. En el centro de administración eliges Roles and administrators, luego New custom role, le das un nombre y seleccionas permisos como microsoft.directory/applications/credentials/update. El conjunto de permisos disponibles para roles personalizados es más reducido que el catálogo integrado y se centra sobre todo en registros de aplicaciones y aplicaciones empresariales, con más áreas que se agregan con el tiempo. Los roles personalizados requieren una licencia Microsoft Entra ID P1. Defines el rol una vez y luego lo asignas, tantas veces como haga falta, en un ámbito.

Toda asignación de rol tiene tres partes: la entidad de seguridad, la definición del rol y el ámbito. La entidad de seguridad es quien recibe el rol, que puede ser un usuario, una entidad de servicio o un grupo asignable a roles. La definición del rol es el conjunto de permisos, integrado o personalizado. El ámbito es donde se aplican los permisos: todo el tenant, una unidad administrativa (un contenedor que agrupa un subconjunto de usuarios, grupos o dispositivos) o un solo recurso, como un registro de aplicación. Asignar el rol Application Administrator solo para una aplicación significa que la persona puede administrar esa aplicación y nada más, lo cual es mucho más seguro que asignarlo en todo el tenant.

Mínimo privilegio significa dar a cada persona el rol más pequeño, en el ámbito más estrecho y por el menor tiempo que le permita hacer su trabajo. En la práctica, eso se traduce en cuatro hábitos. Elegir el rol integrado más específico en lugar de recurrir por defecto a Global Administrator. Limitar los roles a unidades administrativas o recursos individuales cuando sea posible. Usar Privileged Identity Management para que las asignaciones sean elegibles, con activación que exige justificación y MFA, en lugar de estar permanentemente activas. Y revisar las asignaciones con regularidad mediante revisiones de acceso, quitando los roles que las personas ya no usan.

Puedes asignar roles a grupos, lo que simplifica la administración, pero solo si el grupo se creó como asignable a roles. Eso lo controla la propiedad isAssignableToRole, que debe establecerse en true al crear el grupo y no se puede cambiar después, así que no puedes convertir un grupo de seguridad existente. Solo los Global Administrators y los Privileged Role Administrators, además de los propietarios del grupo, pueden administrar la membresía de los grupos asignables a roles. Esto impide que un administrador de menor nivel, como un Groups Administrator, se agregue a sí mismo a un grupo que tiene un rol poderoso y escale así sus privilegios.

Cuando leas una pregunta de mínimo privilegio, resuélvela en orden: identifica la tarea, descarta Global Administrator y Privileged Role Administrator como opciones a menos que la tarea realmente los requiera, luego elige el rol más limitado cuyos permisos aún cubran la tarea y, por último, pregúntate si un ámbito más pequeño o una asignación elegible la haría todavía más segura.

Términos clave

Role definition (definición de rol)
Una colección de permisos, integrada o personalizada, que se puede asignar a una entidad de seguridad.
Role scope (ámbito del rol)
El límite donde se aplica un rol: el tenant, una unidad administrativa o un solo recurso.
Role-assignable group (grupo asignable a roles)
Un grupo creado con isAssignableToRole en true para que pueda recibir asignaciones de roles de Entra; la configuración queda fija al crearlo.
Global Reader
Un rol integrado de solo lectura que puede ver la mayoría de la configuración y los datos sin hacer cambios.
Least privilege (mínimo privilegio)
Otorgar solo los permisos, el ámbito y la duración que una persona necesita para realizar una tarea.
Privileged Authentication Administrator
Un rol que puede administrar los métodos de autenticación de cualquier usuario, incluidos los Global Administrators.
Ejemplo real

Un equipo de mesa de servicio necesita restablecer contraseñas olvidadas del personal común. En lugar de hacerlos User Administrators, el administrador de identidades les asigna el rol Helpdesk Administrator mediante una asignación elegible de PIM, de modo que pueden restablecer contraseñas de no administradores después de activar el rol, pero no pueden crear usuarios ni restablecer la contraseña de un Global Administrator.

Consejo para el examen: Cuando una pregunta pida el rol con menos privilegios, descarta primero Global Administrator y luego elige el rol más específico que aún cubra la tarea. Fíjate en la diferencia entre Authentication Administrator y Privileged Authentication Administrator: solo el privilegiado puede administrar los métodos de los administradores.

Comprueba lo que sabes

¿Cuál es la diferencia entre los roles de Microsoft Entra y los roles de Azure RBAC?

Los roles de Entra administran objetos del directorio como usuarios, grupos y aplicaciones; los roles de Azure RBAC administran recursos de Azure como suscripciones, grupos de recursos y máquinas virtuales.

¿Puedes convertir un grupo de seguridad existente en un grupo asignable a roles?

No. La propiedad isAssignableToRole debe establecerse al crear el grupo y no se puede cambiar después.

¿Qué rol deberías asignar a alguien que solo necesita restablecer contraseñas de usuarios no administrativos?

Helpdesk Administrator (Password Administrator es una opción aún más limitada), no User Administrator ni Global Administrator.

¿Qué licencia requieren los roles personalizados de Entra?

Microsoft Entra ID P1 (o un plan que la incluya).
