Dominio 1: Cluster Architecture, Installation and Configuration (25%)

Consejos para el examen

  • Relaciona el síntoma con el componente: Pods atascados en Pending sin eventos apuntan al scheduler; réplicas que no se crean apuntan al controller-manager; kubectl rechazado en el 6443 apunta al API server; un solo nodo NotReady apunta a su kubelet o a su runtime.
  • Un cgroup driver que no coincide no siempre detiene la instalación; aparece más tarde como Pods inestables o errores del kubelet. Comprueba SystemdCgroup = true en la configuración de containerd y reinicia containerd cada vez que la modifiques.
  • Nodos NotReady y CoreDNS en Pending justo después del init casi siempre significan que todavía no hay ningún plugin CNI instalado, no que el clúster esté roto.
  • Para cambiar una flag del control plane, edita el manifiesto en /etc/kubernetes/manifests en ese nodo, nunca el mirror Pod mediante kubectl. Guarda una copia de seguridad del manifiesto fuera de ese directorio, porque cada archivo YAML que haya dentro se trata como un Pod.
  • Actualizar el paquete no basta: olvidar systemctl daemon-reload && systemctl restart kubelet deja el nodo reportando la versión antigua. Recuerda también usar upgrade apply solo en el primer nodo del control plane y upgrade node en todos los demás.
  • Snapshot save falla con un error de TLS o de deadline si omites --cacert, --cert o --key; copia las rutas directamente del manifiesto de etcd en lugar de adivinarlas. Para la restauración, recuerda que es el volumen hostPath el que realmente decide qué directorio del host ve etcd.
  • Domina las matemáticas del quorum: 3 miembros sobreviven a 1 fallo, 5 sobreviven a 2, y agregar un cuarto miembro a tres no mejora la tolerancia a fallos. Recuerda también que el scheduler y el controller-manager son activo/pasivo, mientras que los API servers son activo/activo.
  • Un RoleBinding que referencia un ClusterRole sigue concediendo acceso solo en el namespace del RoleBinding. Recuerda también que, al suplantar, los sujetos ServiceAccount se escriben como system:serviceaccount:<namespace>:<name>.
  • El examen a menudo pide kubectl drain <node> --ignore-daemonsets (más --delete-emptydir-data si hace falta). Si drain da un error sobre Pods gestionados por un DaemonSet, olvidaste --ignore-daemonsets; si se queja de Pods no gestionados, necesita --force.
  • Las releases de Helm tienen namespace: helm list solo muestra el namespace actual, así que usa helm list -A cuando parezca que falta una release. Y --version se refiere a la versión del chart, no a la de la aplicación.
  • Si kubectl no está disponible, crictl es tu forma de ver lo que pasa en el nodo. Recuerda que Flannel por sí solo no aplica NetworkPolicy; una política que parece ignorada puede simplemente no tener un CNI que la haga cumplir. Relaciona los síntomas rápido: contenedores que no inician significa CRI, ContainerCreating con errores de red significa CNI, PVC en Pending o fallos de montaje significa CSI.
  • Si kubectl apply dice 'no matches for kind', falta la CRD o su grupo/versión no coincide con el apiVersion del objeto. Usa kubectl api-resources para ver exactamente qué kinds y grupos conoce el clúster, y kubectl explain <kind>.spec para ver los campos que permite su esquema.

Términos clave

kube-apiserver
La API REST central del clúster; el único componente que lee y escribe en etcd, y con el que se comunican todos los demás componentes.
etcd
Un almacén clave-valor consistente y distribuido que guarda todo el estado del clúster; atiende a los clientes en el puerto 2379 y a sus pares en el 2380.
kube-scheduler
Asigna los Pods sin programar a nodos filtrando y puntuando los nodos candidatos, y luego vincula el Pod al ganador.
kube-controller-manager
Un único binario que ejecuta muchos bucles de reconciliación, como los controladores de ReplicaSet, Deployment, Node y Job.
kubelet
El agente del nodo, ejecutado por systemd, que inicia los Pods a través del container runtime, ejecuta los probes y reporta el estado.
kube-proxy
El componente por nodo que programa las reglas de reenvío para las IP virtuales de los Services; normalmente se despliega como DaemonSet.
Container runtime (runtime de contenedores)
Software como containerd o CRI-O que descarga imágenes y ejecuta contenedores, controlado por el kubelet mediante la CRI.
cgroup driver
La forma en que el kubelet y el runtime crean los grupos de control; ambos deben usar el mismo, normalmente systemd.
SystemdCgroup
La opción de runc en containerd que hace que containerd use el cgroup driver de systemd.
br_netfilter
Un módulo del kernel que permite a iptables ver el tráfico que cruza un bridge de Linux.
overlay
Un módulo del kernel que proporciona el sistema de archivos por capas que usan las imágenes de contenedor.
net.ipv4.ip_forward
El sysctl que permite al kernel enrutar paquetes entre interfaces, necesario para el tráfico de los Pods.
Preflight checks (comprobaciones previas)
Pruebas que kubeadm ejecuta antes de init o join para detectar errores de configuración del host.
--pod-network-cidr
El rango de IP reservado para las direcciones de los Pods, del que asigna el plugin CNI; no debe solaparse con los rangos de nodos ni de Services.
--control-plane-endpoint
Una dirección compartida y estable para el API server, necesaria para ampliar a alta disponibilidad (HA) más adelante porque se escribe en los certificados.
CNI plugin (plugin CNI)
El complemento de red, como Calico, Cilium o Flannel, que da direcciones y conectividad a los Pods; los nodos están NotReady hasta que se instala uno.
Bootstrap token
Un token de corta duración, 24 horas por defecto, que permite a un nodo que se une autenticarse para solicitar su certificado de kubelet.
discovery-token-ca-cert-hash
Un hash de la clave pública de la CA del clúster que el nodo que se une usa para verificar el control plane.
Static Pod (Pod estático)
Un Pod gestionado directamente por un kubelet a partir de un archivo en su staticPodPath, no por el API server ni por el scheduler.
staticPodPath
El campo de configuración del kubelet que indica el directorio que vigila en busca de manifiestos de static Pods.
Mirror Pod (Pod espejo)
El objeto de solo lectura que el kubelet crea en la API para que un static Pod sea visible con kubectl.
kubeadm certs check-expiration
Lista cada certificado y kubeconfig gestionado por kubeadm y cuándo caduca.
kubeadm certs renew
Vuelve a emitir los certificados gestionados por kubeadm usando la CA existente; los componentes deben reiniciarse para cargarlos.
Kubeconfig context (contexto de kubeconfig)
Una combinación con nombre de un clúster, un usuario y un namespace por defecto.
kubeadm upgrade plan
Comprueba si se puede actualizar y lista las versiones objetivo sin cambiar nada.
kubeadm upgrade apply
Actualiza los componentes del primer nodo del control plane y los complementos del clúster a una versión dada.
kubeadm upgrade node
Actualiza los nodos adicionales del control plane o la configuración del kubelet de un worker.
Version skew policy (política de desfase de versiones)
Reglas sobre cuánto pueden diferir las versiones de los componentes; los kubelets nunca pueden ser más nuevos que el API server.
Minor version (versión minor)
El número del medio en 1.y.z; las actualizaciones con kubeadm deben avanzar una versión minor a la vez.
etcdctl
El cliente de red para un etcd en ejecución; se usa para snapshot save, member list y endpoint health.
etcdutl
La utilidad de etcd sin conexión para trabajar con archivos de datos, incluidos snapshot restore y status.
Snapshot (instantánea)
Una copia de todo el espacio de claves de etcd en un momento dado, guardada en un único archivo.
Data directory (directorio de datos)
La ubicación en disco de la base de datos de etcd, definida por --data-dir y montada mediante un volumen hostPath.
etcd PKI (PKI de etcd)
La CA y los certificados separados en /etc/kubernetes/pki/etcd que se usan para el TLS mutuo de etcd.
Stacked etcd (etcd apilado)
Topología en la que cada nodo del control plane también ejecuta un miembro de etcd.
External etcd (etcd externo)
Topología en la que etcd se ejecuta en hosts separados del control plane.
Quorum
Una mayoría de los miembros de etcd, floor(n/2)+1, necesaria para confirmar escrituras.
--upload-certs
Flag de kubeadm init que cifra los certificados del control plane en el Secret kubeadm-certs e imprime una certificate key.
--certificate-key
La clave que se usa para descifrar los certificados del control plane subidos con --upload-certs al unirse como nodo de control plane.
Leader election (elección de líder)
Mecanismo que mantiene activos un solo scheduler y un solo controller-manager entre todos los nodos del control plane.
Role / ClusterRole
Conjuntos de reglas de permisos, con namespace o de todo el clúster respectivamente.
RoleBinding / ClusterRoleBinding
Objetos que conceden un role a usuarios, grupos o ServiceAccounts, en un namespace o en todo el clúster.
Aggregated ClusterRole (ClusterRole agregado)
Un ClusterRole cuyas reglas se ensamblan automáticamente a partir de otros ClusterRoles que coinciden con un selector de etiquetas.
CertificateSigningRequest
Un objeto de la API que pide a un firmante, como el firmante kube-apiserver-client, que emita un certificado.
kubectl auth can-i
Comprueba si la identidad actual o una identidad suplantada puede ejecutar un verbo sobre un recurso.
Cordon
Marca un nodo como no programable sin tocar los Pods en ejecución.
Drain
Hace cordon de un nodo y desaloja sus Pods para que se reprogramen en otro lugar.
Uncordon
Vuelve a marcar un nodo como programable; los Pods existentes no se devuelven automáticamente.
PodDisruptionBudget
Una política que limita cuántos de los Pods seleccionados pueden estar caídos a la vez por interrupciones voluntarias.
Eviction API (API de desalojo)
La API que usa drain para retirar Pods, y que respeta los PodDisruptionBudgets.
Chart
Un paquete de Helm con manifiestos de Kubernetes en plantillas y valores por defecto.
Release
Una instancia instalada y con nombre de un chart en un namespace, con su propio historial de revisiones.
helm upgrade --install
Instala una release si no existe o la actualiza si ya existe.
Chart version (versión del chart)
La versión del paquete del chart, que se fija con --version; es distinta de la versión de la aplicación que despliega.
kustomization.yaml
El archivo de Kustomize que lista los recursos y las transformaciones; se aplica con kubectl apply -k.
CRI
Container Runtime Interface: la interfaz gRPC que usa el kubelet para controlar container runtimes como containerd y CRI-O.
crictl
Un cliente de línea de comandos para runtimes CRI, usado para depurar a nivel de nodo; funciona sin el API server.
CNI
Container Network Interface: la especificación y los plugins que configuran las interfaces de red y las direcciones IP de los Pods, con la configuración en /etc/cni/net.d y los binarios en /opt/cni/bin.
CSI
Container Storage Interface: la interfaz estándar para drivers de almacenamiento externos al árbol de Kubernetes que aprovisionan, adjuntan y montan volúmenes.
CSIDriver / CSINode
Objetos de la API que listan los drivers CSI instalados y los drivers registrados en cada nodo.
eBPF
Extended Berkeley Packet Filter, una forma de ejecutar programas seguros dentro del kernel de Linux; Cilium lo usa para redes y políticas.
CustomResourceDefinition
Un objeto de apiextensions.k8s.io/v1 que registra un nuevo tipo de recurso en el API server; su nombre es <plural>.<group>.
Custom resource (recurso personalizado)
Una instancia de un tipo definido por una CRD, guardada en etcd y gestionada con kubectl como cualquier objeto.
Storage version (versión de almacenamiento)
La única versión de la CRD marcada como storage: true, que es la versión que se persiste en etcd.
Operator
Un controlador más CRDs que automatiza la operación de una aplicación específica.
Finalizer
Una clave en un objeto que bloquea su borrado hasta que un controlador realiza la limpieza y la quita.

Dominio 2: Workloads and Scheduling (15%)

Consejos para el examen

  • Editar el número de réplicas de un Deployment no crea una nueva revisión; solo lo hacen los cambios en la plantilla de Pod. Y nunca edites directamente un ReplicaSet que pertenece a un Deployment, porque el Deployment lo sobrescribirá. Después de cualquier cambio, ejecuta kubectl rollout status para confirmar que la tarea realmente terminó.
  • Cuando un DaemonSet tiene menos Pods que nodos, antes que nada compara los taints de los nodos (kubectl describe node | grep -i taint) con las tolerations y el nodeSelector de la plantilla de Pod. En los StatefulSets, un Pod atascado suele ser un problema de almacenamiento: describe su PVC.
  • El consumo como variable de entorno nunca se actualiza en vivo; el consumo como volumen sí (excepto con subPath). Si una tarea dice 'haz que los Pods usen el nuevo valor', reinicia la carga de trabajo. En los Secrets, recuerda que base64 es solo una codificación, y decodifica con base64 -d cuando una tarea te pida leer un valor.
  • Si los Pods no existen en absoluto, normalmente la admisión los rechazó (cuota o LimitRange), así que mira los eventos del ReplicaSet. Si los Pods existen pero están en Pending, normalmente la programación falló por requests insuficientes. Los reinicios con OOMKilled significan que el limit de memoria es demasiado bajo.
  • Los términos se combinan con OR y las expresiones dentro de un término con AND. Una etiqueta faltante con affinity required o nodeSelector significa Pending para siempre, nunca una alternativa. Lee primero el evento de Pending; 'didn't match Pod's node affinity/selector' apunta a las etiquetas, mientras que 'Insufficient' apunta a los requests.
  • Una toleration por sí sola no pondrá un Pod en el nodo con el taint; combínala con nodeSelector o affinity. Para quitar un taint se usa el mismo comando con un signo menos al final. Cuando un Pod está en Pending, el evento nombra el taint no tolerado, así que léelo antes de cambiar nada.
  • Lee la topologyKey con cuidado: hostname significa por nodo, zone significa por zona. El mismo selector con una clave distinta da una ubicación completamente diferente. Para tener recuentos equilibrados entre zonas, recurre a topologySpreadConstraints en lugar de anti-affinity.
  • PriorityClass tiene ámbito de clúster y los Pods hacen referencia a ella por su nombre; un error de escritura en priorityClassName hace que la creación del Pod falle en la admisión. Solo se pueden desplazar Pods de menor prioridad. Un Pod en Pending con un valor en NOMINATED NODE está esperando a que terminen sus víctimas de la preemption.
  • Un objetivo <unknown> significa que metrics-server falta o no funciona, o que los Pods no tienen request para ese recurso. Revisa primero kubectl top y luego los requests.
  • Pending con un evento FailedScheduling significa que el scheduler se ejecutó y no encontró nodo. Pending sin ningún evento sugiere que el scheduler no está en ejecución o que el Pod nombra un scheduler que no existe.

Términos clave

ReplicaSet
Un controlador que mantiene en ejecución un número especificado de Pods idénticos que coinciden con un selector.
Deployment
Un controlador que gestiona ReplicaSets para ofrecer rolling updates y rollbacks declarativos.
maxSurge / maxUnavailable
Ajustes de RollingUpdate para los Pods extra permitidos y los Pods que pueden faltar durante una actualización; ambos tienen un valor por defecto del 25 por ciento.
Recreate strategy (estrategia Recreate)
Borra todos los Pods viejos antes de crear los nuevos; causa tiempo de inactividad, pero nunca ejecuta dos versiones juntas.
revisionHistoryLimit
Cuántos ReplicaSets viejos conserva un Deployment para hacer rollback.
kubectl rollout restart
Desencadena un reemplazo gradual de todos los Pods cambiando una anotación en la plantilla de Pod.
DaemonSet
Un controlador que ejecuta una copia de un Pod en cada nodo elegible, con actualizaciones RollingUpdate u OnDelete.
StatefulSet
Un controlador que da a los Pods nombres ordinales estables, DNS estable y almacenamiento persistente por Pod.
Headless Service
Un Service con clusterIP None que publica registros DNS individuales de los Pods, requerido por los StatefulSets.
volumeClaimTemplates
El campo del StatefulSet que crea un PVC por Pod, como data-db-0.
partition
Un ajuste del rolling update de un StatefulSet que actualiza solo los Pods con un ordinal igual o superior al número indicado.
Control plane taint (taint del control plane)
node-role.kubernetes.io/control-plane:NoSchedule, que mantiene los Pods ordinarios fuera de los nodos del control plane.
ConfigMap
Un objeto que guarda configuración no confidencial como pares clave-valor o archivos completos.
Secret
Un objeto para datos sensibles; por defecto los valores están codificados en base64, no cifrados.
envFrom
Importa todas las claves de un ConfigMap o Secret como variables de entorno.
subPath
Una opción de montaje de volumen que monta una sola clave o ruta; esos montajes nunca reciben actualizaciones.
Immutable ConfigMap/Secret (inmutable)
Un objeto con immutable: true cuyos datos no se pueden cambiar después de crearlo.
Encryption at rest (cifrado en reposo)
Configuración del API server que cifra los datos de los Secrets antes de guardarlos en etcd.
Request (solicitud)
La cantidad de CPU o memoria reservada para un contenedor y usada en las decisiones de programación.
Limit (límite)
El máximo de CPU (se estrangula) o de memoria (se termina por OOM) que puede usar un contenedor.
Allocatable (asignable)
La capacidad de un nodo disponible para los Pods tras las reservas del sistema y de Kubernetes; la programación compara los requests con ella.
LimitRange
Una política de admisión de namespace para valores por defecto, mínimos, máximos y proporciones entre limit y request por contenedor o por Pod.
ResourceQuota
Un tope por namespace sobre el uso agregado de recursos y la cantidad de objetos.
QoS class (clase QoS)
Guaranteed, Burstable o BestEffort, derivada de los requests y limits y usada para el orden de desalojo.
nodeName
Un campo del Pod que lo fija directamente a un nodo, evitando al scheduler y sus comprobaciones.
nodeSelector
Un mapa simple de etiquetas que un nodo debe cumplir por completo para que el Pod se programe ahí.
Required node affinity (afinidad obligatoria)
requiredDuringSchedulingIgnoredDuringExecution: una regla estricta de programación; el Pod se queda en Pending si ningún nodo la cumple.
Preferred node affinity (afinidad preferida)
preferredDuringSchedulingIgnoredDuringExecution: una regla flexible con peso (de 1 a 100) que influye en la puntuación pero no bloquea la programación.
IgnoredDuringExecution
Las reglas solo se comprueban en el momento de la programación; los cambios posteriores de etiquetas no mueven los Pods en ejecución.
Taint (marca de repulsión)
Una clave, un valor y un efecto en un nodo que repelen a los Pods sin una toleration coincidente.
Toleration (tolerancia)
Un ajuste del Pod que permite, pero no obliga, la programación en nodos con taints coincidentes.
NoSchedule / PreferNoSchedule
Efectos que bloquean, o desaconsejan de forma flexible, los Pods nuevos que no los toleran, sin afectar a los que ya se ejecutan.
NoExecute
Un efecto de taint que desaloja los Pods en ejecución que no lo toleran, además de bloquear los nuevos.
tolerationSeconds
Cuánto tiempo puede quedarse un Pod que tolera un taint NoExecute antes de ser desalojado.
operator: Exists
Una coincidencia de toleration por clave (y efecto) sin importar el valor; con la clave vacía tolera todos los taints.
topologyKey
Una etiqueta de nodo cuyo valor define un dominio de topología, como un nodo (kubernetes.io/hostname) o una zona (topology.kubernetes.io/zone).
Pod affinity (afinidad de Pods)
Una regla que coloca un Pod en los dominios que ya ejecutan Pods que coinciden con un selector.
Pod anti-affinity (anti-afinidad de Pods)
Una regla que mantiene un Pod alejado de los dominios que ya ejecutan Pods que coinciden con un selector.
topologySpreadConstraints
Reglas que limitan qué tan desigual es la distribución de los Pods coincidentes entre dominios.
maxSkew
La diferencia máxima permitida en la cantidad de Pods coincidentes entre el dominio más cargado y el menos cargado.
whenUnsatisfiable
DoNotSchedule convierte una spread constraint en una regla estricta; ScheduleAnyway la convierte en una preferencia de puntuación.
PriorityClass
Un objeto con ámbito de clúster que asigna una prioridad entera a los Pods que hacen referencia a él por su nombre.
Preemption (desplazamiento)
El scheduler desaloja Pods de menor prioridad para hacer espacio a un Pod en Pending de mayor prioridad.
nominatedNodeName
Un campo del status del Pod que nombra el nodo donde la preemption le está liberando espacio.
globalDefault
Un indicador de PriorityClass que la convierte en la clase por defecto para los Pods que no indican ninguna.
preemptionPolicy: Never
Da a una clase prioridad en la cola sin permitirle desalojar a otros Pods; el valor por defecto es PreemptLowerPriority.
system-node-critical / system-cluster-critical
Clases integradas de prioridad muy alta, reservadas para los componentes esenciales del clúster.
HorizontalPodAutoscaler
Un controlador que ajusta el número de réplicas de una carga de trabajo para cumplir un objetivo de métrica.
metrics-server
Un complemento que recolecta el uso de CPU y memoria de los kubelets y sirve la Resource Metrics API.
averageUtilization
Un objetivo expresado como porcentaje de los requests de recursos de los Pods.
Stabilization window (ventana de estabilización)
Un periodo durante el cual el HPA tiene en cuenta recomendaciones anteriores antes de escalar; se usa sobre todo para frenar el escalado hacia abajo y evitar el flapping.
Vertical Pod Autoscaler
Un complemento que recomienda o define los requests de los contenedores según el uso observado.
Cluster Autoscaler
Un complemento que agrega o elimina nodos según los Pods en Pending y la utilización de los nodos.
Binding (asignación)
El acto de asignar un Pod a un nodo, registrado al definir spec.nodeName.
Static Pod
Un Pod que el kubelet arranca directamente desde un archivo de manifiesto en su staticPodPath, sin el API server ni el scheduler.
staticPodPath
El ajuste de configuración del kubelet que indica el directorio de manifiestos de static Pods, /etc/kubernetes/manifests en clústeres de kubeadm.
Mirror Pod (Pod espejo)
La representación en la API de un static Pod, que pertenece al Node y no se puede editar.
schedulerName
Un campo del Pod que indica qué scheduler debe ubicarlo; por defecto, default-scheduler.

Dominio 3: Services and Networking (20%)

Consejos para el examen

  • Recuerda qué componente es dueño de qué rango: el Pod CIDR lo usan el CNI y el controller-manager, y el Service CIDR, el API server y kube-proxy. No deben solaparse entre sí ni con la subred de los nodos.
  • No uses ping para probar un ClusterIP; prueba el puerto. Si un nodo no puede alcanzar los Services mientras otros sí, sospecha primero del Pod de kube-proxy de ese nodo.
  • port es el puerto del Service, targetPort es el puerto del contenedor y nodePort es el puerto del nodo. Confundir port y targetPort es la causa más común de un Service que existe pero rechaza las conexiones.
  • Una EndpointSlice vacía significa que el selector no coincide con ningún Pod en Ready; revisa las etiquetas y la readiness antes de culpar a kube-proxy. Para externalTrafficPolicy, recuerda: Local conserva la IP de origen, Cluster reparte la carga.
  • Cuenta los guiones: podSelector y namespaceSelector bajo un mismo guion se combinan con Y; bajo guiones separados, con O. Y un deny de egress sin una excepción para DNS lo rompe todo.
  • Si una ruta se ignora, revisa ambos lados de la adjunción: parentRefs (incluidos sectionName y namespace) y el allowedRoutes del listener. Las condiciones de estado te dicen qué lado se negó.
  • La coincidencia Prefix es por segmento de ruta, no por prefijo de cadena: /app coincide con /app/x, pero no con /application. Y el Secret de TLS debe estar en el mismo namespace que el Ingress.
  • El Service se llama kube-dns, pero los Pods y el ConfigMap se llaman coredns. dnsPolicy Default no es la predeterminada; lo es ClusterFirst.
  • Prueba siempre desde un Pod con el mismo namespace y las mismas etiquetas que el cliente real, o los resultados de las NetworkPolicies te engañarán. Define un timeout en cada prueba y recuerda que busybox tiene wget, no curl.

Términos clave

Pod CIDR
El rango de direcciones del que se asignan las IP de los Pods, definido al crear el clúster con --pod-network-cidr.
Service CIDR
El rango de direcciones para los ClusterIP de los Services, definido por --service-cluster-ip-range en el API server.
CNI plugin (plugin CNI)
Un plugin de red, llamado por el runtime de contenedores, que da a cada Pod una interfaz y una IP y conecta los Pods entre nodos.
Pause container (contenedor pause)
El contenedor sandbox que mantiene el network namespace compartido de un Pod.
Overlay network (red overlay)
Una encapsulación (como VXLAN) que transporta el tráfico de los Pods entre nodos a través de la red de los nodos.
ClusterIP
Una IP virtual para un Service, implementada como reglas de reenvío y no como una interfaz real.
kube-proxy
Un agente por nodo, ejecutado como DaemonSet en clústeres de kubeadm, que programa las reglas de reenvío de los Services a partir de los Services y las EndpointSlices.
iptables mode (modo iptables)
Modo de kube-proxy que usa cadenas NAT (KUBE-SERVICES, KUBE-SVC, KUBE-SEP) para reenviar el tráfico de los Services.
IPVS mode (modo IPVS)
Modo de kube-proxy que usa el balanceador de carga basado en hash IP Virtual Server del kernel; se inspecciona con ipvsadm.
nftables mode (modo nftables)
Modo de kube-proxy que programa las reglas con el framework nftables; se inspecciona con nft.
NodePort

Dominio 4: Storage (10%)

Consejos para el examen

  • Los PVCs en Pending casi siempre se deben a una discrepancia en storageClassName, modo de acceso, tamaño, volumeMode o selector. Compara los campos del PVC y del PV lado a lado con kubectl get -o yaml y revisa los eventos con kubectl describe pvc.
  • RWO es por nodo, no por Pod. Si la pregunta dice que solo un Pod puede usar el volumen en todo momento, la respuesta es ReadWriteOncePod. Si muchos nodos deben escribir, la respuesta es ReadWriteMany sobre almacenamiento compartido.
  • El aprovisionamiento dinámico usa Delete por defecto. Si el examen te pide conservar los datos de un claim aprovisionado dinámicamente, cambia el PV a Retain con un patch antes de borrar el PVC.
  • Omitir storageClassName significa 'usa la predeterminada'; definirlo como cadena vacía significa 'sin clase'. Se comportan de forma muy distinta, y al examen le gusta evaluar justamente eso.
  • Pending con 'waiting for first consumer' es el estado esperado hasta que un Pod use el claim. No definas nodeName en esos Pods, porque omite al scheduler que desencadena la vinculación.
  • Expande el PVC, nunca el PV, y solo hacia arriba. Si la edición se rechaza, revisa primero allowVolumeExpansion en la StorageClass del claim; si CAPACITY se retrasa, busca FileSystemResizePending.
  • El API server rechaza un PV local sin nodeAffinity. Los datos de hostPath se quedan en un nodo, así que si el Pod se mueve, sus datos no. NFS necesita las herramientas de cliente en cada nodo.
  • La retención predeterminada es Retain tanto para whenDeleted como para whenScaled, así que borrar un StatefulSet no borra sus datos. Los nombres de los PVCs siguen el patrón plantilla-statefulset-ordinal.

Términos clave

PersistentVolume (PV)
Un objeto de alcance de clúster que representa una porción de almacenamiento y sus propiedades.

Una solicitud de almacenamiento con namespace que se vincula a exactamente un PV coincidente.

El campo del PV que registra a qué PVC está, o estuvo, vinculado.

Indica si un volumen se presenta como un sistema de archivos montado (Filesystem) o como un dispositivo sin formato (Block); debe coincidir para la vinculación.

Dominio 5: Troubleshooting (30%)

Consejos para el examen

  • Ready Unknown significa que el kubelet dejó de reportar; Ready False significa que reporta un problema. En ambos casos, systemctl status kubelet y journalctl -u kubelet en el nodo son tus dos primeros comandos.
  • Si no hay ningún contenedor en crictl ps -a, el manifiesto no se pudo analizar (revisa el journal del kubelet); si el contenedor se cae, el componente arrancó pero rechazó su configuración (revisa crictl logs).
  • Lee el mensaje FailedScheduling completo: los conteos te dicen por qué se rechazó cada grupo de nodos, y la solución es distinta para cada uno. Recuerda que el scheduler usa los requests, no el uso en tiempo real.
  • kubectl top muestra el uso real; describe node muestra los requests y limits. Las decisiones de scheduling se basan en los requests, así que 'uso bajo pero los Pods no se programan' es un problema de requests.
  • En un CrashLoopBackOff, la salida útil casi siempre está en kubectl logs <pod> --previous. En los Pods con varios contenedores, indica siempre -c.
  • Los eventos no se ordenan por tiempo de forma predeterminada y caducan después de más o menos una hora; agrega --sort-by y filtra con --field-selector type=Warning para eliminar el ruido rápidamente.
  • Endpoints vacíos significa selector o readiness; endpoints presentes pero conexión rechazada significa targetPort o la aplicación; funciona en un nodo pero no en otro significa kube-proxy o el CNI de ese nodo.
  • CoreDNS en CrashLoopBackOff con una línea de log 'Loop detected' es el problema del stub de systemd-resolved; corrige el resolvConf del kubelet o el destino de forward, no el plugin loop.
  • Refused significa que nada está escuchando (API server caído o dirección equivocada); x509 significa certificados; Unauthorized significa credenciales; Forbidden significa RBAC. El error te dice qué capa corregir.
  • Pon las expresiones jsonpath entre comillas simples, revisa la estructura del objeto con -o yaml antes de escribir la ruta y usa siempre cat sobre el archivo de respuesta después.
  • Los Pods de StatefulSet en un nodo perdido no se reemplazan automáticamente; el borrado forzado (o el taint de fuera de servicio) es la solución, pero solo después de confirmar que el nodo está realmente caído.
