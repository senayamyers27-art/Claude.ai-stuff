Certified Kubernetes Administrator CKA (Kubernetes v1.35 curriculum)

Preparar los hosts para kubeadm: containerd, cgroup driver systemd coincidente, swap, módulos overlay y br_netfilter, sysctls de ip_forward y bridge, y puertos requeridos

kubeadm arranca un clúster, pero da por hecho que cada host ya está preparado: un container runtime instalado, el kernel configurado para la red de contenedores y el kubelet capaz de gestionar recursos. Sus preflight checks (comprobaciones previas) se ejecutan antes de kubeadm init y kubeadm join y te detienen si algo de esto está mal, imprimiendo líneas que empiezan con [ERROR ...]. El examen Certified Kubernetes Administrator (CKA) puede pedirte que arregles un host que no las supera, así que conviene conocer cada requisito y por qué existe en lugar de memorizar un script.

Empieza por el container runtime. containerd es la opción más común. Instálalo, genera una configuración por defecto con containerd config default > /etc/containerd/config.toml y asegúrate de que las opciones del runtime runc tengan SystemdCgroup = true. Los control groups (cgroups, grupos de control) son la función de Linux que limita y contabiliza la CPU y la memoria por proceso, y un cgroup driver es el método que se usa para crearlos y gestionarlos. En distribuciones basadas en systemd, el kubelet usa por defecto el cgroup driver systemd cuando lo configura kubeadm, y el runtime debe usar el mismo driver. Si el kubelet y el runtime no coinciden, dos gestores se pelean por el mismo árbol de recursos: los Pods e incluso el nodo pueden volverse inestables, con contenedores que se reinician y mensajes sobre cgroups en el log del kubelet. Reinicia containerd después de editar el archivo con systemctl restart containerd y habilítalo para que arranque al iniciar el sistema.

Luego, el swap. Históricamente, el kubelet se negaba a arrancar con el swap activado, porque el intercambio a disco hace impredecibles los límites de memoria y las decisiones de eviction (desalojo). El paso de preparación estándar sigue siendo desactivarlo: swapoff -a para el sistema en ejecución, y comentar las líneas de swap en /etc/fstab para que siga desactivado después de un reinicio. Olvidar el segundo paso es una trampa clásica: todo funciona hasta que el nodo se reinicia, y entonces el kubelet falla. Las versiones más recientes de Kubernetes han añadido soporte configurable para swap, pero salvo que una tarea indique lo contrario, lo seguro es esperar que el swap esté desactivado.

La red de contenedores necesita dos módulos del kernel. overlay da soporte al sistema de archivos overlay que usan las imágenes de contenedor, apilando capas de imagen de solo lectura bajo una capa de contenedor con permisos de escritura. br_netfilter hace que el tráfico que cruza un bridge (puente) de Linux sea visible para iptables, algo importante porque muchos plugins CNI (Container Network Interface, interfaz de red de contenedores) conectan los Pods mediante un bridge y las reglas de Service de kube-proxy viven en iptables. Carga los módulos ahora con modprobe y hazlos persistentes en un archivo dentro de /etc/modules-load.d/ para que se carguen al arrancar. Después configura los sysctls para que el kernel reenvíe paquetes entre interfaces y haga pasar el tráfico del bridge por iptables. Hazlos persistentes en un archivo dentro de /etc/sysctl.d/ y aplícalos con sysctl --system.

cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
sudo modprobe overlay && sudo modprobe br_netfilter
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.ipv4.ip_forward = 1
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
EOF
sudo sysctl --system

Puedes verificar cada paso rápidamente. lsmod | grep -e overlay -e br_netfilter muestra los módulos cargados. sysctl net.ipv4.ip_forward debería imprimir = 1. swapon --show no debería imprimir nada. grep SystemdCgroup /etc/containerd/config.toml debería mostrar true. Ten en cuenta que los sysctls de bridge solo existen una vez cargado br_netfilter, y por eso el paso del módulo va primero; si sysctl --system se queja de que una clave net.bridge es desconocida, falta el módulo.

Por último, los puertos. Los nodos del control plane necesitan que estén accesibles, según corresponda, el 6443 (API server), el 2379 y el 2380 (cliente y pares de etcd), el 10250 (API del kubelet), el 10257 (controller-manager) y el 10259 (scheduler). Los worker nodes necesitan el 10250 más el rango de NodePort, de 30000 a 32767 por defecto. Tu plugin CNI también puede necesitar sus propios puertos, así que revisa su documentación. Si hay un firewall en el host, estos son los puertos que debes abrir; un 6443 bloqueado suele manifestarse como un join que agota el tiempo de espera al intentar llegar al API server.

El último paso es instalar las propias herramientas de Kubernetes. Instala kubeadm, kubelet y kubectl en versiones coincidentes desde el repositorio de paquetes de Kubernetes y bloquéalas para que las actualizaciones rutinarias no las actualicen por sorpresa, por ejemplo con apt-mark hold kubelet kubeadm kubectl en Debian o Ubuntu. Habilita el servicio del kubelet. No te preocupes si en este punto el kubelet se reinicia en bucle: está esperando a que kubeadm le dé una configuración, y se estabiliza en cuanto se ejecuta init o join. En el examen, si un host no supera el preflight, lee cada línea [ERROR] al pie de la letra: nombra el archivo, el módulo o el puerto exacto que está mal, y corregir exactamente eso suele ser todo lo que pide la tarea. Resiste la tentación de usar --ignore-preflight-errors salvo que la tarea lo permita explícitamente, porque oculta los problemas reales en lugar de resolverlos.

Términos clave

cgroup driver
La forma en que el kubelet y el runtime crean los grupos de control; ambos deben usar el mismo, normalmente systemd.
SystemdCgroup
La opción de runc en containerd que hace que containerd use el cgroup driver de systemd.
br_netfilter
Un módulo del kernel que permite a iptables ver el tráfico que cruza un bridge de Linux.
overlay
Un módulo del kernel que proporciona el sistema de archivos por capas que usan las imágenes de contenedor.
net.ipv4.ip_forward
El sysctl que permite al kernel enrutar paquetes entre interfaces, necesario para el tráfico de los Pods.
Preflight checks (comprobaciones previas)
Pruebas que kubeadm ejecuta antes de init o join para detectar errores de configuración del host.
Ejemplo real

kubeadm init no supera el preflight con un mensaje que indica que el contenido de /proc/sys/net/ipv4/ip_forward no está establecido en 1. Agregas net.ipv4.ip_forward = 1 a /etc/sysctl.d/k8s.conf, ejecutas sysctl --system y vuelves a ejecutar init, que ahora pasa.

Consejo para el examen: Un cgroup driver que no coincide no siempre detiene la instalación; aparece más tarde como Pods inestables o errores del kubelet. Comprueba SystemdCgroup = true en la configuración de containerd y reinicia containerd cada vez que la modifiques.

Comprueba lo que sabes

¿Qué dos módulos del kernel se cargan al preparar un host para kubeadm y por qué?

overlay para el sistema de archivos de las imágenes de contenedor y br_netfilter para que el tráfico de los Pods que pasa por el bridge atraviese iptables.

¿Dónde haces persistentes los valores de sysctl para que sobrevivan a un reinicio?

En un archivo dentro de /etc/sysctl.d/, aplicado con sysctl --system.

¿Cuál es el rango de NodePort por defecto que debe estar abierto en los nodos?

De 30000 a 32767.

¿Por qué el kubelet y containerd deben usar el mismo cgroup driver?

De lo contrario, dos gestores manejan el mismo árbol de cgroups de forma distinta, lo que provoca Pods y nodos inestables.
