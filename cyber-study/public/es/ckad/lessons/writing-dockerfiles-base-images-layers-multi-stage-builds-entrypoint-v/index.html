Escribir Dockerfiles: imágenes base, capas, builds multietapa, ENTRYPOINT vs CMD

Una imagen de contenedor es un sistema de archivos empaquetado más metadatos que indican cómo iniciar tu aplicación. Un Dockerfile es la receta para construirla: un archivo de texto plano con instrucciones que el builder ejecuta de arriba hacia abajo. Aquí el examen Certified Kubernetes Application Developer (CKAD) se ubica en el dominio Application Design and Build, y espera que sepas leer, corregir y escribir Dockerfiles cortos. Eso significa saber qué hace cada instrucción común, cómo se almacena el resultado y qué comando ejecutará realmente el contenedor terminado.

Todo Dockerfile parte de una imagen base con FROM, por ejemplo FROM python:3.12-slim o FROM alpine. La base aporta los archivos del sistema operativo y, a menudo, un runtime de lenguaje. Las bases más pequeñas, como las imágenes slim, alpine o distroless, implican descargas más rápidas en cada nodo y menos paquetes instalados que podrían contener vulnerabilidades, por eso los escáneres de seguridad las recomiendan tan a menudo. Después de FROM normalmente ves un conjunto predecible de instrucciones. WORKDIR fija el directorio de trabajo para los pasos siguientes y para el contenedor en ejecución. COPY trae archivos desde el contexto de build. RUN ejecuta comandos de build, como instalar dependencias. ENV define variables de entorno que persisten en el contenedor. EXPOSE documenta un puerto de escucha, pero no publica ni abre nada por sí solo. USER deja de usar root para que la aplicación se ejecute con menos privilegios.

Las capas son la siguiente idea que debes entender, porque explican tanto la velocidad del build como el tamaño de la imagen. Las instrucciones que modifican el sistema de archivos, principalmente RUN, COPY y ADD, crean cada una una nueva capa de solo lectura apilada sobre las anteriores. Las capas se guardan en caché: si una instrucción y todo lo anterior no han cambiado, el builder reutiliza la capa en caché en lugar de ejecutarla de nuevo, y en la salida del build ves ese paso marcado como cached. La caché es ordenada, así que en cuanto un paso cambia, todos los pasos posteriores deben ejecutarse otra vez. Por eso copias el manifiesto de dependencias (como requirements.txt o package.json) e instalas las dependencias antes de copiar el resto del código fuente. Así, editar un archivo fuente solo invalida las capas posteriores, y la lenta instalación de dependencias se reutiliza. Las capas también explican una sorpresa sobre el tamaño: borrar un archivo en una capa posterior no reduce la imagen, porque la capa anterior todavía lo contiene. Para mantener un archivo temporal fuera de la imagen, créalo y elimínalo en el mismo paso RUN, o usa una etapa de build separada.

Un build multietapa resuelve el problema del tamaño y de la superficie de ataque de forma más limpia. Usa más de un FROM en el mismo archivo. La primera etapa, a menudo nombrada con AS build, tiene compiladores y herramientas de build. La etapa final parte de una imagen de runtime pequeña y copia solo el artefacto terminado con COPY --from=build. Las herramientas de build, el código fuente y las cachés nunca llegan a la imagen que distribuyes, lo que la hace más pequeña y más rápida de descargar, y le da a un atacante menos herramientas si alguna vez el contenedor se ve comprometido. Solo la última etapa se convierte en la imagen de salida, a menos que elijas otro target.

FROM golang:1.22 AS build
WORKDIR /src
COPY go.mod ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /app

FROM alpine
COPY --from=build /app /app
USER 1000
ENTRYPOINT ["/app"]
CMD ["--port", "8080"]

Lee el ejemplo desde arriba. La etapa de build descarga los módulos antes de copiar el código fuente, así que las descargas de módulos siguen en caché aunque edites el código. La etapa final empieza desde cero con alpine, toma solo el binario compilado /app, cambia al usuario 1000 y define el comando de inicio. Nada de la cadena de herramientas de Go termina en la imagen distribuida.

ENTRYPOINT y CMD juntos definen ese comando de inicio, y a las preguntas del examen les encanta preguntar qué se ejecuta realmente. ENTRYPOINT es el ejecutable que siempre se ejecuta. CMD aporta argumentos por defecto que son fáciles de sobrescribir. Cuando ambos están presentes, el contenedor ejecuta ENTRYPOINT seguido de CMD, así que el ejemplo anterior ejecuta /app --port 8080. Si ejecutas la imagen con argumentos adicionales, como docker run myimage --port 9090, estos reemplazan a CMD pero mantienen ENTRYPOINT, lo que da /app --port 9090. Si solo está definido CMD, es el comando completo, y cualquier argumento que pases lo reemplaza por completo. Reemplazar el propio ENTRYPOINT requiere una sobrescritura explícita, como docker run --entrypoint o, en Kubernetes, el campo command del Pod.

Por último, la forma en que los escribes importa para un apagado limpio. Prefiere la forma exec, un arreglo JSON como ["/app"], en lugar de la forma shell ENTRYPOINT /app. La forma exec ejecuta tu programa directamente como proceso 1 (PID 1, el primer proceso del contenedor), así que recibe señales como SIGTERM cuando Kubernetes detiene el Pod y puede terminar las solicitudes y salir de forma ordenada. La forma shell envuelve el programa en /bin/sh -c, y el shell puede no reenviar las señales. Entonces Kubernetes espera a que se agote el periodo de gracia de terminación y mata el contenedor a la fuerza, lo que se nota como despliegues lentos y conexiones cortadas. Cuando inspeccionas una imagen terminada, docker image inspect muestra el Entrypoint y el Cmd configurados, una forma rápida de confirmar qué se ejecutará.

Términos clave

Base image (imagen base)
La imagen indicada en FROM que aporta el sistema de archivos inicial y el runtime para tu build.
Layer (capa)
Un cambio de sistema de archivos de solo lectura y en caché, producido por una instrucción como RUN o COPY.
Build cache (caché de build)
La reutilización de capas anteriores cuando una instrucción y todo lo anterior no han cambiado.
Multi-stage build (build multietapa)
Un Dockerfile con varias etapas FROM en el que solo se copian artefactos seleccionados a la imagen final.
ENTRYPOINT
El ejecutable fijo que el contenedor ejecuta al iniciar.
CMD
Argumentos por defecto (o un comando por defecto si no hay ENTRYPOINT) que se reemplazan con los argumentos dados en tiempo de ejecución.
Exec form (forma exec)
La forma de arreglo JSON de ENTRYPOINT o CMD, que ejecuta el programa directamente como PID 1 para que reciba señales.
Ejemplo real

La imagen de Python de un equipo tardaba cuatro minutos en reconstruirse tras cada cambio de código. Movieron COPY requirements.txt . y RUN pip install -r requirements.txt por encima de COPY . ., de modo que la capa de dependencias quedó en caché y los rebuilds bajaron a segundos. Pasar a un build multietapa también redujo el tamaño de la imagen final a menos de la mitad, y cambiar CMD python app.py por CMD ["python", "app.py"] permitió que la aplicación recibiera SIGTERM y se apagara rápidamente durante los despliegues.

Consejo para el examen: Recuerda la regla de combinación: ENTRYPOINT más CMD se ejecutan juntos, y los argumentos en tiempo de ejecución reemplazan solo a CMD. Las preguntas suelen pedir qué comando ejecuta realmente un contenedor, así que escríbelo palabra por palabra antes de responder.

Comprueba lo que sabes

¿Por qué deberías copiar el archivo de dependencias e instalar los paquetes antes de copiar el resto del código fuente?

Porque las capas se guardan en caché en orden; así, los cambios de código solo invalidan las capas posteriores, y la lenta instalación de dependencias se reutiliza desde la caché.

Una imagen tiene ENTRYPOINT ["ping"] y CMD ["localhost"]. ¿Qué se ejecuta si la inicias con el argumento example.com?

ping example.com, porque los argumentos en tiempo de ejecución reemplazan a CMD mientras ENTRYPOINT se mantiene.

¿Qué logra un build multietapa?

Mantiene las herramientas de build y los archivos intermedios fuera de la imagen final, haciéndola más pequeña y reduciendo la superficie de ataque.

¿Por qué preferir ENTRYPOINT ["/app"] en lugar de ENTRYPOINT /app?

La forma exec ejecuta /app como PID 1, así que recibe SIGTERM directamente; la forma shell lo ejecuta bajo /bin/sh -c, que puede no reenviar las señales, lo que provoca apagados lentos y forzados.
