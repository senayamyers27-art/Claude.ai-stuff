Construir, etiquetar, guardar y cargar imágenes con docker o podman (build, tag, save, load)

Una vez que tienes un Dockerfile, lo conviertes en una imagen con un motor de contenedores. Docker y Podman aceptan comandos casi idénticos, así que en el examen Certified Kubernetes Application Developer (CKAD) normalmente puedes escribir lo mismo con cualquiera de las dos herramientas, cambiando solo la primera palabra. Podman funciona sin un daemon central en segundo plano y puede ejecutarse sin root (rootless), es decir, como un usuario normal, pero para construir, etiquetar y mover imágenes el flujo de trabajo es el mismo. Esta lección recorre ese flujo en el orden en que lo usarías.

Primero se construye. docker build -t myapp:1.0 . construye una imagen. El flag -t le da un nombre y una etiqueta, y el . final es el contexto de build: el directorio cuyos archivos se envían al builder y pueden referenciarse con COPY y ADD. Los archivos fuera del contexto son invisibles para el build, por eso COPY ../secrets . falla. Si el Dockerfile tiene otro nombre o ubicación, apúntalo con -f path/to/Dockerfile manteniendo el contexto donde está. Un archivo .dockerignore en la raíz del contexto mantiene fuera del build los archivos grandes o sensibles, como .git, node_modules locales o credenciales, lo que acelera el build e impide que se cuelen secretos en una capa.

Lo siguiente que debes hacer exactamente bien es el nombre, porque las tareas del examen verifican el nombre y la etiqueta con precisión. Una referencia de imagen tiene la forma registry/repository:tag, por ejemplo registry.example.com/team/myapp:1.0. Si omites el registro, se asume Docker Hub. Si omites la etiqueta, se asume latest, que es solo una etiqueta por defecto y no significa la más reciente. Una etiqueta es un rótulo movible que apunta a una imagen. La identidad inmutable es el digest de contenido, escrito myapp@sha256:..., que cambia si cambia un solo byte de la imagen. docker tag myapp:1.0 registry.example.com/team/myapp:1.0 agrega un segundo nombre a la misma imagen sin copiar nada, algo que haces antes de docker push a un registro. Ejecutar docker images después muestra ambos nombres con el mismo IMAGE ID, lo que prueba que apuntan a una sola imagen.

A veces no hay registro, por ejemplo en un host aislado de la red (air-gapped) o en una tarea del examen que te pide exportar una imagen a un archivo. docker save -o myapp.tar myapp:1.0 escribe la imagen, con todas sus capas, etiquetas y configuración, en un archivo tar. docker load -i myapp.tar la importa en otra máquina, y la imagen reaparece con su nombre y etiqueta originales. Podman admite los mismos comandos save y load, y también puede guardar en formato OCI (Open Container Initiative, el estándar de imágenes neutral respecto a proveedores) con --format oci-archive. No los confundas con docker export y docker import. Estos trabajan sobre el sistema de archivos aplanado de un contenedor, así que pierden el historial de capas y metadatos como ENTRYPOINT, CMD, variables de entorno y puertos expuestos. Por eso una imagen importada a menudo no tiene ningún comando de inicio.

docker build -t myapp:1.0 .
docker tag myapp:1.0 myapp:latest
docker images | grep myapp
docker save -o /tmp/myapp.tar myapp:1.0
docker load -i /tmp/myapp.tar

Llevar una imagen construida localmente a un clúster local es un paso aparte, porque los nodos del clúster no ven las imágenes almacenadas en tu estación de trabajo. Con kind (Kubernetes in Docker) ejecutas kind load docker-image myapp:1.0. Con minikube puedes usar minikube image load myapp:1.0. Ambos copian la imagen al runtime de contenedores del nodo. Luego, en la especificación del Pod, define imagePullPolicy: IfNotPresent o Never para que el kubelet, el agente de cada nodo, use la imagen cargada en lugar de intentar descargarla de un registro. Cuidado con el valor por defecto: para una imagen con la etiqueta latest, o sin etiqueta, la política de descarga por defecto es Always, que falla con ErrImagePull y luego ImagePullBackOff si la imagen solo existe localmente. Para cualquier otra etiqueta el valor por defecto es IfNotPresent, una razón más para dar a las imágenes etiquetas de versión específicas.

Los comandos de inspección te ayudan a confirmar tu trabajo antes de entregarlo. docker images (o podman images) lista las imágenes con su repositorio, etiqueta, ID y tamaño. docker image inspect myapp:1.0 imprime el Entrypoint, el Cmd, el entorno y los puertos expuestos configurados, para que verifiques que el comando de inicio se conservó. docker history myapp:1.0 muestra cada capa, la instrucción que la creó y su tamaño, una forma rápida de detectar un paso inesperadamente grande.

En conjunto, una tarea típica de estilo examen se lee como una lista de verificación: construir desde un directorio dado con un nombre y una etiqueta dados, quizá agregar una segunda etiqueta y luego guardar en una ruta exacta. Lee la ruta y la etiqueta dos veces, usa save en lugar de export, y termina con ls -lh sobre el archivo para saber que existe y tiene un tamaño razonable.

Términos clave

Build context (contexto de build)
El directorio enviado al builder cuyos archivos pueden alcanzar COPY y ADD.
.dockerignore
Un archivo en el contexto de build que lista las rutas que se excluyen del build.
Tag (etiqueta)
Un rótulo legible y movible, como 1.0, que apunta a una imagen.
Digest
El hash de contenido sha256 inmutable que identifica una imagen de forma única.
docker save / load
Comandos que exportan imágenes con todas sus capas y metadatos a un archivo tar y las vuelven a importar.
docker export / import
Comandos que trabajan sobre el sistema de archivos aplanado de un contenedor y descartan el historial y los metadatos de la imagen, como CMD.
imagePullPolicy
Campo del Pod (Always, IfNotPresent o Never) que controla cuándo el kubelet descarga una imagen de un registro.
Ejemplo real

Una tarea de estilo examen dice: construye la imagen desde /opt/app con el nombre webapp y la etiqueta v2, y luego guárdala en /opt/webapp-v2.tar. Ejecutas podman build -t webapp:v2 /opt/app seguido de podman save -o /opt/webapp-v2.tar webapp:v2, luego verificas con ls -lh /opt/webapp-v2.tar y, si el tiempo lo permite, con podman image inspect webapp:v2 para confirmar el comando de inicio.

Consejo para el examen: Las tareas que piden un archivo de imagen quieren save (imagen con capas y metadatos), no export (el sistema de archivos plano de un contenedor). Lee dos veces el nombre, la etiqueta y la ruta de salida exactos, y verifica que el archivo existe antes de continuar.

Comprueba lo que sabes

¿Qué significa el punto final en docker build -t app:1 .?

Define el contexto de build como el directorio actual, que se envía al builder y es desde donde COPY puede leer.

Cargaste una imagen llamada app:latest en kind, pero el Pod muestra ErrImagePull. ¿Por qué?

Para una etiqueta latest, la imagePullPolicy por defecto es Always, así que el kubelet intenta un registro; define imagePullPolicy como IfNotPresent o Never, o usa una etiqueta específica.

¿docker tag copia la imagen?

No, solo agrega otro nombre que apunta al mismo contenido de la imagen.

¿Qué comando muestra las capas de una imagen y sus tamaños?

docker history <image> (o podman history).
