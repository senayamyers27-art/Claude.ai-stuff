Logs de contenedores: kubectl logs con -c, -f, --previous, --tail, --since, -l y deploy/<name>

Empieza por saber de dónde vienen los logs. Se espera que los contenedores escriban sus logs en la salida estándar (stdout) y en la salida de error estándar (stderr). El runtime de contenedores de cada nodo captura esos dos flujos en archivos, y cuando ejecutas kubectl logs, el API server le pide al kubelet de ese nodo que te los devuelva. Este diseño tiene una consecuencia directa: si una aplicación escribe solo en un archivo dentro del contenedor, como /var/log/app.log, kubectl logs no muestra absolutamente nada. Esa es una de las razones del patrón sidecar, en el que un pequeño contenedor auxiliar sigue el archivo de log y lo imprime en su propio stdout para que la plataforma pueda recogerlo.
