AWS Certified Developer – Associate DVA-C02

Código resiliente: reintentos con retroceso exponencial y jitter, idempotencia, tiempos de espera, fallas parciales y colas de mensajes fallidos

Los sistemas distribuidos fallan de maneras pequeñas todo el tiempo. Una solicitud se limita porque un servicio se está protegiendo, una llamada de red agota su tiempo de espera o un servicio de destino devuelve un error por un momento mientras escala. El código resiliente cuenta con esto y responde de forma medida en lugar de bloquearse o empeorar las cosas. El examen AWS Certified Developer – Associate (DVA-C02) evalúa si conoces las técnicas estándar, qué falla resuelve cada una y qué funciones de AWS las implementan.

Los reintentos son la primera herramienta, pero solo para errores transitorios. Buenos candidatos son la limitación (ThrottlingException, ProvisionedThroughputExceededException, HTTP 429), los errores de servidor HTTP 5xx y los tiempos de espera de red agotados, porque es muy posible que la misma solicitud tenga éxito un momento después. Reintentar un error de validación, una solicitud mal formada o un AccessDenied solo repite la falla y pierde tiempo, porque nada de la solicitud cambió. Reintentar de inmediato en un bucle cerrado es directamente dañino: todos los clientes golpean al mismo tiempo al servicio que está en problemas, lo que lo mantiene sobrecargado.

El retroceso exponencial resuelve el problema del bucle cerrado esperando más después de cada intento fallido, por ejemplo 100 milisegundos (ms), luego 200 ms, 400 ms y 800 ms, hasta un retraso máximo y un número máximo de intentos. El jitter agrega aleatoriedad a cada espera. Sin él, miles de clientes que fallaron en el mismo momento reintentarían todos en el mismo momento, recreando el pico en oleadas sincronizadas. Con jitter, sus reintentos se reparten en el tiempo y el servicio puede recuperarse. Los SDK de AWS ya implementan reintentos con retroceso y jitter para las llamadas a las API de AWS; tú configuras el modo de reintento y el número máximo de intentos en lugar de escribir el bucle. Para llamadas a tus propios servicios o a API de terceros, agregas la misma lógica en tu código o con una biblioteca de reintentos.

La idempotencia es lo que hace seguros los reintentos. Una operación es idempotente si realizarla dos veces tiene el mismo efecto que realizarla una vez. Esto importa porque los duplicados son normales en AWS: un reintento del SDK puede reenviar una solicitud que en realidad tuvo éxito, las colas estándar de SQS entregan los mensajes al menos una vez y Lambda reintenta las invocaciones asíncronas fallidas. Tu código debe detectar e ignorar las repeticiones. Las técnicas comunes son una clave de idempotencia proporcionada por el cliente, como un ID de pedido o de pago; una escritura condicional de DynamoDB como attribute_not_exists(orderId), que falla con ConditionalCheckFailedException si el elemento ya se procesó; y la idempotencia natural, como establecer un estado en SHIPPED en lugar de incrementar un contador.

Los tiempos de espera evitan que una sola dependencia lenta consuma todos tus recursos. Configura tiempos de espera explícitos de conexión y de lectura en los clientes HTTP y del SDK, y hazlos más cortos que el tiempo de espera de tu función o solicitud. Así tu código recupera el control a tiempo para registrar el problema, reintentar o devolver un error limpio, en lugar de ser terminado a mitad de la operación sin una línea de registro útil. Una función Lambda detrás de Amazon API Gateway, por ejemplo, debe abandonar una llamada lenta a un servicio de destino mucho antes de que se cumpla el tiempo de espera de integración del propio API Gateway, para que el cliente reciba una respuesta significativa en lugar de un error genérico del gateway.

La falla parcial ocurre cuando un lote contiene elementos buenos y malos. Si un registro de un lote de diez falla y tu código lanza un error para todo el lote, se reintenta el lote completo, incluidos los nueve que ya tuvieron éxito, lo que desperdicia trabajo y puede crear duplicados. Las API por lotes informan resultados por elemento para que puedas evitarlo: BatchWriteItem de DynamoDB devuelve UnprocessedItems, y SendMessageBatch de SQS devuelve una lista de entradas fallidas. Tu código debe reintentar solo esas, idealmente con retroceso. Para las funciones Lambda que leen de SQS, Kinesis o DynamoDB Streams, las respuestas parciales de lote te permiten informar solo los elementos fallidos para que Lambda reintente únicamente esos.

Una cola de mensajes fallidos (DLQ, dead-letter queue) es adonde van los mensajes después de fallar un número determinado de veces. Su función es lidiar con un mensaje envenenado (poison message), uno que nunca podrá procesarse con éxito, quizás porque su JSON está mal formado o hace referencia a un registro que ya no existe. Sin una DLQ, un mensaje envenenado sigue volviendo, desperdicia cómputo y, en sistemas ordenados, bloquea todo lo que viene detrás. En SQS asocias una política de reenvío (redrive policy) a la cola de origen con un maxReceiveCount; cuando un mensaje se ha recibido esa cantidad de veces sin eliminarse, SQS lo mueve a la DLQ. Las invocaciones asíncronas de Lambda pueden enviar los eventos fallidos a una cola SQS o un tema SNS configurado como DLQ de la función, o a un destino en caso de falla (on-failure destination) más completo.

Una DLQ solo sirve si alguien se da cuenta de lo que contiene. Crea una alarma de Amazon CloudWatch sobre la métrica ApproximateNumberOfMessagesVisible de la DLQ, investiga lo que llega ahí, corrige la causa y luego reenvía los mensajes a la cola de origen. Juntas, estas técnicas forman un patrón al que el examen vuelve a menudo: reintentar los errores transitorios con retroceso y jitter, hacer que los handlers sean idempotentes, limitar cada llamada con un tiempo de espera, reintentar solo los elementos fallidos de un lote y atrapar lo que quede en una DLQ monitoreada.

Términos clave

Exponential backoff (retroceso exponencial)
Una estrategia de reintento en la que la espera entre intentos crece de forma multiplicativa, lo que reduce la presión sobre un servicio en problemas.
Jitter
Variación aleatoria agregada a los retrasos de reintento para que muchos clientes no reintenten en oleadas sincronizadas.
Idempotency (idempotencia)
La propiedad por la que repetir una operación produce el mismo resultado que hacerla una vez, lo que hace seguros los reintentos y las entregas duplicadas.
Poison message (mensaje envenenado)
Un mensaje que falla al procesarse cada vez que se recibe y que se repetiría para siempre sin una cola de mensajes fallidos.
Dead-letter queue (DLQ, cola de mensajes fallidos)
Una cola que recibe los mensajes o eventos que fallaron al procesarse después de un número configurado de intentos, para inspeccionarlos más tarde.
Idempotency key (clave de idempotencia)
Un valor único, como un ID de pedido, enviado con una solicitud para que el receptor pueda detectar e ignorar repeticiones de la misma operación.
Redrive policy (política de reenvío)
La configuración de SQS que indica una cola de mensajes fallidos y el maxReceiveCount a partir del cual los mensajes fallidos se mueven a ella.
Ejemplo real

Una función Lambda de pagos procesa mensajes de SQS. Registra cada ID de pago en DynamoDB con un put condicional que usa attribute_not_exists, así que un mensaje entregado dos veces se cobra una sola vez. Su cola SQS tiene una política de reenvío con un maxReceiveCount de 5 y una DLQ, y una alarma de CloudWatch se activa cuando la DLQ contiene algún mensaje.

Consejo para el examen: Si una pregunta menciona errores de limitación como ProvisionedThroughputExceededException o ThrottlingException, la respuesta casi siempre es reintentos con retroceso exponencial (y jitter), no simplemente agregar más reintentos ni aumentar los tiempos de espera.

Comprueba lo que sabes

¿Por qué agregar jitter al retroceso exponencial?

Sin aleatoriedad, los clientes que fallaron juntos reintentan juntos y recrean el pico de carga; el jitter reparte los reintentos en el tiempo.

¿Qué errores no deben reintentarse?

Los errores del cliente que volverán a fallar sin cambios, como los errores de validación, las solicitudes mal formadas o AccessDenied; reintenta solo los errores transitorios como la limitación, los 5xx y los tiempos de espera agotados.

¿Cómo ayuda una DLQ con un mensaje envenenado en SQS?

Cuando el número de recepciones del mensaje supera el maxReceiveCount, SQS lo mueve a la DLQ, así deja de reintentarse y de bloquear el procesamiento, y puedes inspeccionarlo.

Una función Lambda procesa un lote de diez mensajes de SQS y uno falla. ¿Cómo evitas volver a procesar los nueve exitosos?

Habilita las respuestas parciales de lote (ReportBatchItemFailures) y devuelve solo el ID del mensaje fallido, para que solo ese mensaje se reintente.
